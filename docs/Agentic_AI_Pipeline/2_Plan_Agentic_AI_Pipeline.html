1 · Summary — read this first

What we are building, what it costs, what could go wrong

The problem. The walkthrough shows a complete agentic system on paper: an overnight data load fails at 02:14 from a renamed column, and four agents plus a human fix it safely before the 08:00 deadline. Kazi wants to learn agentic AI by building that system for real — and to end up with a portfolio piece that proves it, not a demo that only works on a laptop.

The recommendation. Build it in 9 phases over 20 weeks at 2–3 hours a week, following the architecture page, in Python throughout.

  • Stack. Strands Agents SDK for the agents; Amazon Bedrock (Nova Micro) for the model; S3 for raw files; PostgreSQL with pgvector for the analytics table and RAG; DynamoDB for memory (apa-memory) and approvals (apa-approvals); Step Functions plus SNS for the human approval.
  • Where it runs. Phases 1–7 on the Mac: the pipeline job, the agent runtime, the MCP tool servers and the publisher run locally with uv against Docker Postgres, and call Bedrock, S3, DynamoDB and X-Ray as real AWS services through the scoped kazi-dev-apa role (never an admin profile). Step Functions, EventBridge, SNS and the approve endpoint are real AWS from the start; a small local worker polls Step Functions for work, so the cloud orchestrator can drive code that lives on the Mac (ADR-012). Phase 8 swaps the worker for Lambda invokes and deploys the same code to Lambda and RDS.
  • How it ships. One project, apa, in your existing aws-data-platform repo. Every change to AWS goes through a pull request and the platform’s OIDC pipeline (main is protected); each new AWS service the pipeline must learn to create is a small platform change, reviewed the same way and deployed by you.
  • Proof. Every one of the 20 terms from the walkthrough is built, in a named phase, with a test that proves it works.

The cost. About US $1–3 a month while building (Bedrock tokens and S3, essentially), provided the database lives on the Mac during development and RDS (with a NAT gateway or VPC endpoints for the Lambdas) is only switched on for the final demo day, then deleted (with a snapshot). If RDS is left running 24/7 it adds about $13–15 a month on its own, and a forgotten NAT gateway about $42 — see §10 and ADR-004. The platform’s budget is US $5 a month, and its budget brake freezes dev and prod if actual spend reaches it, so the building months fit with room to spare and the Phase 8 demo month is the one to watch.

The top three risks. (1) Time: 2–3 hours a week is thin, so phases are sized to one sitting each and every phase ends in something working. (2) Bedrock in a guard-railed account: Nova Micro works in Sydney by its plain model ID, but the account’s region guardrail (an SCP) allows only ap-southeast-2 and us-east-1, so any cross-region inference profile (apac., au., us.) is refused — which puts the Claude Haiku comparison in Phase 7 in doubt. Spike B tests this before any agent runs, and the decision is recorded in ADR-002. (3) Scope creep: all 20 terms is a lot, so the plan is phased with gates — a phase does not start until the previous one passes its checks.

What I am asking you to approve. This plan as written — stack, phases, budget rule, and the definition of done for each phase. No code is written until you say yes. If you disagree with any ADR in §8, that is the place to argue: each one names the alternative it rejected.

2 · Goals, non-goals, constraints

What “done” means — and what it does not

Goals

  • Learn by building, not by reading. Every term in the walkthrough is implemented, not just described. If a term has no code and no test, it is not done.
  • End with a portfolio piece. A public-ready repo with a README a stranger can follow, architecture docs, tests, a recorded demo of the 02:14 incident fixing itself, and a cost screenshot proving it stayed under the $5 budget.
  • Stay under US $5 a month, every month. That is the platform’s budget, and the budget brake enforces it by freezing dev and prod, so it is a design constraint, not a hope. §10 prices every service; §11 names the traps.
  • Fit a real calendar. 2–3 hours a week, on a Mac, in Python at “can write scripts, not apps” level. Phases are sized to that.

Non-goals (explicitly out of scope)

  • Production readiness for real customer data. This uses synthetic customer data only. No real PII, ever.
  • High availability, multi-region, or scale beyond one nightly run. One run a night, on demand, is the load.
  • A managed-agent service (Bedrock Agents, AgentCore Runtime) as the primary runtime. We build on the SDK so the learning is in the code, not the console.
  • Fine-tuning a model. Prompting, tools, retrieval and guardrails are the levers here.

4 · C4 level 2 — Containers

The deployable pieces

Each box here is something that runs separately or stores data separately. Three things to notice: the agents never touch production data directly — they only call tools, and every data path (Postgres, memory, approvals) starts at the MCP tool servers; the database is drawn once (local Docker in Phases 1–7, RDS in Phase 8) because it is one responsibility; and the approval path has its own table and endpoint, separate from agent memory, so no agent can approve its own work.

Figure 2a — Containers. The pipeline (top band) and the agent runtime (second band) are separate deployables joined by one event: a failed load, which Step Functions catches and hands to the Orchestrator. The same two-headed arrow carries the answer back (“approval needed”, later “done”). The runtime reasons through Bedrock and acts only through the MCP tool servers; the tool servers are the only containers with database and table access — Postgres, apa-memory, and read-only access to apa-approvals. Postgres is shown once: where it runs (Docker on the Mac in Phases 1–7, RDS in Phase 8) is a deployment decision (ADR-004), not a second database. In Phases 1–7 the “Mac” boxes are reached from Step Functions through a worker that polls for tasks (ADR-012); in Phase 8 the same functions are invoked as Lambdas. Step Functions’ last state invokes the publisher, which reads verified numbers from Postgres and writes the static site. All containers emit logs to CloudWatch and traces to X-Ray (one trace per incident).

The approval path and its trust boundary

The one place where a human, not an agent, changes what the system may do. It is drawn separately because its value is in what is missing: no arrow from any agent reaches the green box.

Figure 2b — Approval path. Steps 1–5 are the human’s part: the request, the email, a deliberate click, the record, the resume. 5 · C4 level 3 — Components

Inside the agent runtime

Only one container is complex enough to need a level-3 diagram: the agent runtime. Everything in it is a Python module with one job. If a module's job cannot be stated in one sentence, it is two modules.

Figure 3 — Agent runtime components. The Orchestrator is the hub: it briefs each specialist and validates every handoff before the next agent acts — no agent hands work directly to another. The four specialist agents are Strands Agent objects with different system prompts and different tool allow-lists — not four codebases. The interesting engineering lives in the supporting modules: the context builder (what the agent is allowed to see), the guardrail hooks (what it is never allowed to do), and the handoff package (how agents pass work without losing information). When approval is needed the runtime returns control to Step Functions, which sends the SNS email and waits — the wait does not live in the agent runtime. The Verifier checks through MCP tools like every other agent; it has no direct Postgres access. Memory works the same way: the memory client calls MCP tools (save_note, recall_lessons), so the runtime holds no data credentials at all.

Interfaces — the contracts agents must honour

MCP tools (each a FastMCP tool, each with a typed schema). read_job_logs(job, since) → log lines; get_table_schema(table) → columns; search_runbook(query) → ranked chunks with sources; save_note(incident, note) and recall_lessons(topic) → short-term notes and long-term lessons in apa-memory; write_test_copy(mapping) → row count + errors + hash; run_checks(table) → the 4 checks with pass/fail; swap_tables(test, live, mode) → mode=swap is only callable after approval, enforced by the tool server reading the apa-approvals record (matching incident AND test-copy hash, unexpired, unused), not by the agent promising; mode=rollback restores customers_prev; publish_mapping(version) → records mapping v2 so tomorrow's load uses it. The tool server connects to Postgres as the role mapped to the authenticated agent (the Fixer gets read-production, write-staging); only swap_tables, after its approval check, uses the separate swapper role that can rename live tables. The Verifier calls run_checks through MCP like every other agent — it has no direct Postgres access. Tools return data, never prose. An agent that wants a fact calls a tool; an agent that guesses is a bug.

A2A messages. Task request / task accepted / task result, using the A2A protocol over HTTP between the Orchestrator and the specialists, each behind a local endpoint (localhost) in Phase 6. Before Phase 6, and in the Phase 8 Lambda (where the specialists share one runtime), the same message shapes travel in-process — same schema, different transport, so only the transport changes, not the logic. The A2A path is proven locally in Phase 6.

Handoff package (validated, typed).

{
  "done": "cause confirmed: column rename",
  "next": "update mapping, reload tonight's data",
  "owner": "fixer-01",
  "evidence": ["log 02:14 'Column not found'",
               "schema diff source vs mapping",
               "change note 17:40 yesterday"],
  "do_not_touch": ["analytics.customers (live)"]
}

Human approval payload (SNS email). What broke, what was tested (test-copy row count, errors, and the Verifier's 4-check result), exactly what will change (swap customers_test → customers, publish mapping v2), and what happens if it is not approved. The email links to a confirmation page on the approve endpoint (Lambda Function URL) — a scanner prefetching the link cannot approve (opening the page changes nothing); approving needs a deliberate click, which POSTs a single-use token: Step Functions’ own task token, AWS-issued, unguessable and accepted once. The endpoint writes the approval to apa-approvals (a conditional put, so it cannot overwrite) and resumes the state machine with that token. No approval, no swap — the swap tool refuses without a matching approval record.

Matching approval, defined. A record in apa-approvals matches only if it names this incident ID, the hash of this test copy as it is now, has not expired, and has not been applied before (its ID is not yet in applied_approvals). The swap tool checks all four; a record that fails any of them is refused. The swap transaction inserts the approval ID into applied_approvals, so a replay fails on the unique key. Rollback is the same tool in reverse, authorised by the record that authorised the swap: the Verifier only reports a failed live check, the Orchestrator briefs the Fixer, and the Fixer calls swap_tables with mode=rollback. The Step Functions wait (waitForTaskToken) times out after 30 minutes — if the human has not approved by then, the incident stays open and the live table is untouched.

8 · Architecture decisions

ADRs — each decision, and what it beat

Status: ACCEPTED — ADR-001…010 were decided by Kazi on 18 Nov 2026 (some amended in later drafts, as noted in each). ADR-011 and ADR-012 are DRAFT until this plan is approved. These live in the repo at projects/apa/docs/adr/ from Phase 0.

ADR-001 — Strands Agents SDK as the agent framework

Context. The system needs a model-driven agent loop, MCP tool consumption, multi-agent patterns, human-approval interrupts, and tracing — and the builder is learning, so the framework must not demand framework expertise first.

Decision. Use Strands Agents SDK (Python), with Amazon Bedrock as the model provider.

Alternatives considered. LangGraph — explicit graph control and the best debugging story, but every step is hand-wired, which is more framework to learn before the first agent runs. Bedrock Agents (managed) — no code, but the learning goal is the code, and console configuration cannot be reviewed in a repo. Raw boto3 + hand-rolled loop — maximum learning about the loop, but re-implements retries, tool parsing and interrupts badly.

Consequences. Fastest path to a working agent; MCP and A2A are native, not adapters. Cost: the agent loop's behaviour is partly the framework's, so the plan includes reading the loop code in Phase 2 rather than treating it as magic. Revisit if: Strands cannot express the approval handoff cleanly in Phase 4 — LangGraph is the named fallback.

ADR-002 — Amazon Bedrock, Nova Micro as the default model

Context. Agents need a model that is cheap enough to run hundreds of learning iterations, available in ap-southeast-2, and capable enough to follow tool schemas.

Decision. Bedrock with Nova Micro by default; Claude Haiku used for one comparison run in Phase 7 so the evals can show the cost/quality trade-off with numbers.

Model access. Bedrock now grants access to serverless foundation models by default — no per-model access request. Anthropic models still need a one-time usage form. Nova Micro is in-region in Sydney: the plain model ID amazon.nova-micro-v1:0 worked in a 21 Nov test run, and Phase 0 Spike B records the confirmed IDs (Nova Micro and Titan v2) here. The account’s guardrails SCP denies every region except ap-southeast-2 and us-east-1. A cross-region inference profile (apac., au., us.) is refused if any region it can route to is blocked — and the au. profile routes to Melbourne (ap-southeast-4). Current Claude models are normally reached only through such a profile, so the Phase 7 Haiku comparison needs a decision, to be recorded here: (a) a deliberate, reviewed change to the guardrails SCP (a human deploy from the management account), (b) an older in-region Claude model if the test shows one is available, or (c) compare against a second in-region Amazon model instead.

Alternatives considered. Claude Sonnet as default — better reasoning, but roughly 10–20× the token price; unjustifiable while the loop itself is what is being learned. Local models via Ollama — free, but tool-calling reliability on small local models is poor and would teach the wrong lessons about agent behaviour. OpenAI API — fine model, wrong cloud: it adds a second bill and a second credential for no benefit.

Consequences. Model spend stays in cents. The evals in Phase 5 are model-specific and must be re-run if the model changes — that is documented, not hidden. Revisit if: Nova Micro fails the tool-calling evals in Phase 5 (pass mark: 20-case set ≥ 17/20, §11); Haiku becomes the default (which needs option (a) or (b) above) and the cost model is re-priced.

ADR-003 — PostgreSQL + pgvector for the table, the sandbox, and RAG

Context. The system needs a relational analytics table, a scratch copy for safe testing, and vector search over runbooks. The budget forbids a dedicated vector database.

Decision. One PostgreSQL database (pgvector extension) holds customers, customers_test, customers_prev (rollback), applied_approvals (single-use ledger) and the documents embedding table.

Alternatives considered. Bedrock Knowledge Bases + OpenSearch Serverless — the AWS-native RAG path, but OpenSearch Serverless has a ~$70/month minimum: seven times the entire budget, before a single query. DynamoDB + a separate vector store — two stores, two bills, and DynamoDB is a poor fit for the analytics table. SQLite + local vectors — free, but SQLite cannot be the deployed analytics table, so the deployment would diverge from development.

Consequences. One database to learn, one to pay for, and retrieval quality is measurable with a 10-question test. Cost: pgvector at 1.2M-row scale is not a production vector store; nobody should claim it is. Revisit if: retrieval precision falls below the Phase 3 pass mark after chunking and prompt fixes.

ADR-004 — Mac-local for Phases 1–7; RDS only for the Phase 8 demo, then deleted

Context. The account is paid and new (accounts created after 15 Jul 2025 get a credit balance, not 12 months of free RDS hours), so no free RDS is assumed; Spike A checks the credit balance. An RDS db.t3.micro left running costs ~$13–15/month — over budget alone. And a cloud Lambda cannot reach a database on the Mac, so the topology must be decided before any phase is written: either the database moves to the cloud (and the plan must price the VPC), or the code runs on the Mac (and Phase 8 is the deployment).

Decision. Phases 1–7 run on the Mac: the pipeline job, the agent runtime and the MCP tool servers run locally with uv against PostgreSQL in Docker, calling Bedrock, S3, DynamoDB, SNS and X-Ray as real AWS services via the kazi-dev-apa profile; Step Functions and EventBridge stay in the cloud and drive the Mac through a polling worker (ADR-012). The deployed Lambda path (ADR-005/ADR-010) is the Phase 8 target, not how Phases 1–7 execute — no phase's definition of done requires a cloud Lambda to reach the Mac. RDS is deployed once, in Phase 8, for the recorded demo, and deleted the same day (with a snapshot) — not stopped, because a stopped RDS instance auto-restarts after 7 days. This keeps Phases 1–7 free of VPC costs: no NAT gateway, no VPC endpoints. Phase 8 does need that path, for the demo day only — priced in §10.

Alternatives considered. RDS from Phase 1, left running — simplest, but breaches the budget every month. RDS from Phase 1 in a VPC — Lambdas in a VPC need NAT or VPC endpoints to reach Bedrock and SNS; NAT alone adds ~$30/month and breaks the budget. RDS started/stopped per session — saves money but adds a start/stop ritual to every 2-hour session and teaches nothing. Neon/Supabase free tier — genuinely free Postgres with pgvector, but it moves the database off AWS and weakens the “built on AWS” portfolio story.

Consequences. Build cost stays at $1–3/month and no VPC is needed until Phase 8. The deployment step is practised exactly once, deliberately, in Phase 8 — and the demo recording is the evidence it worked. The Mac-local code and the deployed Lambda code are the same Python (uv packaging, ADR-009), so Phase 8 is a deployment change, not a rewrite. Revisit if: Spike A finds a credit balance large enough to cover RDS and a NAT gateway for the whole build — credits expire, so even then the Mac-local decision stands and credits are a bonus for the Phase 8 demo day.

ADR-005 — Lambda for every job and tool; no EC2, no AgentCore Runtime as primary

Context. Jobs and tools need somewhere to run. The always-free Lambda allowance (1M requests + 400,000 GB-seconds/month) covers this workload many times over.

Decision. Ingest, transform, MCP tool servers, the agent runtime and the publisher all run as Lambda functions in the deployed (Phase 8) topology, and locally on the Mac during Phases 1–7 (ADR-004, ADR-012). The approve endpoint is a Lambda in every phase. No EC2.

Alternatives considered. Bedrock AgentCore Runtime — the managed agent host, but it is pay-per-use with no free tier and hides the runtime the portfolio is meant to demonstrate. EC2 t3.micro — a familiar server, but it must be patched, kept running, and paid for when idle. ECS/Fargate — the right answer at real scale, and the wrong answer for one nightly run.

Consequences. Zero idle cost; cold starts are irrelevant at one run a night. Cost: Lambda's 15-minute limit constrains the transform job — the seeded load is sized to finish in under 5 minutes, and the plan says so explicitly. The human approval wait never sits inside a Lambda — Step Functions holds it with waitForTaskToken (§7), so the 15-minute cap cannot be hit by an 18-minute human. Revisit if: a phase needs a long-running process (it should not — see §11).

ADR-006 — Step Functions orchestrates the pipeline; Strands orchestrates the agents

Context. Two different orchestration problems exist: the nightly pipeline (a fixed sequence with a failure branch) and the incident response (a goal split into tasks, with a human decision in the middle). One tool for both would be a compromise.

Decision. Step Functions owns the pipeline: schedule → load → on failure, invoke agents → on approval-needed, send the SNS email and hold the wait with waitForTaskToken (30-minute timeout) → on approval, resume → on success, publish and finish. In Phases 1–7 the load, incident, resume and publish states are Activities served by the Mac worker (ADR-012); in Phase 8 they become Lambda invokes. Strands owns the agent teamwork: the Orchestrator agent splits the goal and delegates. The boundary is the failure event, and the return is the approval decision.

Alternatives considered. Everything in Step Functions — visible and robust, but agent reasoning does not belong in a state machine; every prompt change becomes a deployment. Everything in Strands — the pipeline schedule and retries would be re-implemented in Python for no benefit. Cron + Lambda chaining — works, but failures are invisible compared with a state-machine execution view.

Consequences. Each orchestrator does what it is good at, and the portfolio shows both. Cost: two things to learn instead of one — Phase 1 teaches Step Functions before any agent exists, so the learning is sequenced.

ADR-007 — DynamoDB for memory; no separate memory service

Context. Agents need short-term memory (this run) and long-term memory (past incidents). Managed memory services exist, but they are another bill and another API.

Decision. DynamoDB table apa-memory, on-demand, inside the always-free allowance. Short-term notes are written per run; long-term lessons are explicit records, not embeddings. Approvals are NOT stored here — they live in apa-approvals (ADR-011), in a separate trust boundary. Agents reach this table only through MCP tools (save_note, recall_lessons).

Alternatives considered. Bedrock AgentCore Memory — managed and good, but pay-per-use and it would hide the memory design the portfolio is meant to show. Postgres for memory too — possible, but mixing run memory into the analytics database blurs the boundary the architecture is trying to teach. Files on disk / in S3 — free, but no querying and no story about memory as a system component.

Consequences. Memory is a visible, testable design: the Phase 3 test proves a lesson changes the diagnosis. Cost: DynamoDB's data model (partition/sort keys) must be learned in Phase 3 — it is scoped to one table and one access pattern, deliberately.

ADR-008 — Evals are a fixed 20-case set, run on every change; no eval platform

Context. “It worked once” is not evidence. The portfolio needs repeatable proof that the agents behave — and that a change did not break them.

Decision. A versioned set of 20 eval cases (10 retrieval, 5 diagnosis, 5 end-to-end incident replays) run by a plain pytest script, scored automatically, with results committed to the repo. No third-party eval platform.

Alternatives considered. LangSmith / Langfuse hosted — better tooling, but another account, another bill, and hosted traces of a learning project. Manual “try it and see” — the default for tutorials and the reason most agent demos cannot be trusted. ADR-009 — uv as the Python package and environment manager

Context. The project needs reproducible Python environments on the Mac and in CI, with pinned dependencies a reviewer can reproduce exactly. Phase 0 needs to name one tool for this, not leave it to chance.

Decision. Use uv (Astral) for everything Python: uv python install 3.13 for the interpreter, uv init / uv add for dependencies, uv sync to build the environment, uv run to execute. Dependencies are declared in pyproject.toml and pinned in the committed uv.lock lockfile.

Lambda packages. On the Mac and in tests, everything runs under uv run. For Lambda (Phase 8) the platform’s pipeline does the packaging: scripts/cfn-change.sh runs aws cloudformation package, which zips the folder a template’s Code property points at and uploads it to the platform’s artifacts bucket under a name derived from its contents, so new code always reaches the function (decision D7 in the repo’s docs/decisions.md). cfn-lint warns that a local folder only works once packaged (W3002), so each such function says in its own Metadata that this is intended, and the lint check stays green. Alternatives considered. pip + venv (original plan) — works, but no lockfile, so “works on my machine” is a real risk for a portfolio repo. Consequences. Reproducible environments from one lockfile; faster installs; one tool instead of three. Cost: uv is a new tool to learn in Phase 0 — budgeted there, about 30 minutes, and it replaces the venv lesson rather than adding to it. ADR-011 — Approvals in their own DynamoDB table; only the approve endpoint writes

Context. The swap must not run without a human approval, and the approval must be checkable by the tool that performs the swap. If the approval record lives in the same table the agents write memory to, any agent that can write memory can approve its own work — the Fixer could approve itself.

Decision. A separate DynamoDB table apa-approvals, on-demand, inside the always-free allowance. Only the approve endpoint's IAM role (a Lambda Function URL) can write to it; the tool servers' role can only read it, and the agent runtime has no direct access (agents reach data only through MCP). The record is bound to the incident ID, the hash of the test copy, and an expiry. swap_tables reads the record and refuses unless it matches this incident AND the hash of customers_test as it is right now, is unexpired, and has not been applied before. Single use is enforced where the swap happens: the swap transaction inserts the approval ID into applied_approvals (unique key) in Postgres, so a second swap with the same approval fails and the swap tool never needs write access to apa-approvals.

How the link works. Step Functions' approval step sends the SNS email with waitForTaskToken; the link carries the incident ID, the test-copy hash and Step Functions' own task token (AWS-issued, unguessable, accepted once). Opening the link shows a confirmation page and changes nothing, so a scanner prefetching it cannot approve. Only the POST behind a deliberate click writes the record (a conditional put) and resumes the state machine. If the hash in the link is edited, the swap tool compares against the real hash and refuses.

Alternatives considered. Approval record in apa-memory — one fewer table, but the Fixer writes memory, so it could write its own approval; rejected on the trust boundary. Key-scoped IAM on one table — DynamoDB item-level IAM is coarse and hard to audit; a separate table is a clearer boundary. A used flag in apa-approvals set by the swap tool — the tool would then need write access to the table that is supposed to be write-only for the endpoint; the Postgres ledger gives single use atomically with the swap instead. Approval as a Step Functions token only, no table — the token proves the human clicked, but the swap tool needs a durable, checkable record tied to the test copy's hash; the token alone does not carry it.

Consequences. The approval is a durable, auditable record a reviewer can read. Cost: one more on-demand table inside the always-free allowance — $0. The approve endpoint is a second Lambda to deploy (Phase 4), and the confirm page is a small static page. IAM, not Postgres roles, enforces this boundary, so it only holds if the identities really are separate: the Mac's kazi-dev-apa profile gets read-only on apa-approvals, and a Phase 4 test proves a PutItem with that profile returns AccessDenied. Revisit if: the approval flow needs more than one approver, in which case the record gains an approver field — the table shape, not the boundary, changes.

ADR-012 — Step Functions Activities bridge the cloud state machine to the Mac in Phases 1–7

Context. ADR-004 runs the code on the Mac for Phases 1–7; ADR-006 puts the pipeline orchestration in Step Functions, which is a cloud service. A cloud state machine cannot call a process on a laptop behind a home router, so without a bridge Phase 1 would need a cloud Lambda reading a database on the Mac, which ADR-004 itself says cannot work.

Decision. The state machine and the EventBridge schedule live in the cloud from Phase 1. Its work states (run the load, run the incident, resume after approval, publish) are Step Functions Activities in Phases 1–7. A small worker on the Mac (src/worker/, run with uv run) long-polls GetActivityTask, runs the same handler function that Lambda will run in Phase 8, and reports SendTaskSuccess or SendTaskFailure. The worker only dials out: no inbound port, no tunnel. In Phase 8 the four states change from Activity to Lambda invoke; the payload contract and the handler code do not. The approval wait is unaffected: waitForTaskToken, SNS and the approve endpoint are cloud services in every phase. Activity timeouts are set to 15 minutes, matching the Lambda cap, so Phase 8 changes nothing about sizing.

Alternatives considered. SQS + waitForTaskToken — the same idea with a queue to create and drain; Activities are the simpler fit. Start executions from the Mac only, no cloud state machine until Phase 8 — simplest, but Phase 1 would teach nothing about Step Functions and Term 1's proof (an execution visible in the console) would not exist until the end. Expose the Mac with a tunnel (ngrok, Tailscale Funnel) — opens an inbound path to a laptop that holds the database; wrong trade for a portfolio repo. Postgres in the cloud from Phase 1 — rejected in ADR-004 on cost.

Consequences. Step Functions is practised properly in Phase 1 and the move to the cloud in Phase 8 is a diff of four states. The state machine only makes progress while the worker runs, so a scheduled 02:00 run needs the Mac awake: the schedule is created but disabled in Phases 1–7, enabled for one test evening and for the Phase 8 demo, and learning runs start from aws stepfunctions start-execution. With no worker, an execution waits for the activity timeout and then fails visibly, not silently. A full incident is about a dozen state transitions, far inside the free 4,000 a month. Cost: one more thing to build in Phase 1 (about 40 lines of boto3 plus the Activity resources); Phase 0 Spike C proves it before anything depends on it. Revisit if: the always-awake requirement becomes a nuisance — the answer is to reach Phase 8, not to add infrastructure.

Phase 4 — Fixer: sandbox, guardrails, policy, identity, human approval (4 weeks) · Terms 5, 9, 10, 16, 17

Entry: Phase 3 gate passedTime: 4 weeksCost: < $1

Goal. The most important phase. The Fixer can repair the table — and cannot destroy it. This is the phase the portfolio is really about.

  • write_test_copy: builds customers_test with the new mapping and loads tonight's files; reports rows and errors.
  • Guardrail hook + tool-server authorisation + Postgres role: any attempt to overwrite the live table in one step is blocked before the call lands, logged, and the agent must re-plan. All three layers refuse independently — test each one on its own (disable the hook and the tool server still refuses; call as the Fixer role and Postgres still refuses). The blocked attempt leaves the live table byte-identical (row count + hash).

The Fixer's Postgres role can read production and write staging, and cannot write production; only swap_tables, after its approval check, uses the separate swapper role. Test tries, and fails. (IAM roles do not control Postgres writes.)

Only the endpoint's IAM role can write to apa-approvals. The service role is widened for SNS first; Lambda, including Function URLs and their permissions, is covered since Phase 0, and DynamoDB since Phase 3. A public Function URL needs two permission statements, lambda:InvokeFunctionUrl and lambda:InvokeFunction. The endpoint is plain Python with no third-party packages, so the pipeline packages it as it is. Test that a PutItem with the Mac's kazi-dev-apa profile returns AccessDenied.

Step Functions holds the wait with waitForTaskToken (30-minute timeout). A timeout or rejection leaves the live table alone and the incident open. (Phase 5 adds the Verifier's 4-check result to the email.)

Definition of done. The full Fixer path runs end to end: blocked overwrite → test copy loads with 0 errors → approval email → confirm page → approval → swap → dashboard fresh. Testing strategy (one paragraph, no hand-waving)

Three layers. Unit tests (pytest) for the context builder, the handoff validator, the guardrail hook, and the check functions — these run in milliseconds and in CI on every push. Integration tests run the tools against the local Docker Postgres and the seeded incident — these run before a phase is called done. Evals (ADR-008) are the 20-case set scored on every change; they are the only test that judges agent behaviour, and they are the gate between phases. No layer substitutes for another: a green unit suite with failing evals means the code is correct and the system is wrong.

Eval pass mark (§11). The 20-case eval set must score ≥ 17/20 (85%) on every run, and the 4 checks must pass 4/4 on a fixed table (test copy and live). A change that drops the eval score below 17/20, or breaks a check, does not merge — the evals are the gate between phases (ADR-008). If Nova Micro cannot reach the pass mark, ADR-002 is revisited (Haiku default) and the cost model is re-priced.
