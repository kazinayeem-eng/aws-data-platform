The replay • The incident in 12 beats

02:00 to 08:00, in order

    The team

    Four specialists, one coordinator — hub-and-spoke

    Same Strands runtime, different system prompt and tool allow-list — and the allow-list is enforced by the tool server per agent identity, not just by the runtime. Every handoff passes through the Orchestrator.

    Data • Four stores, one job each

    Why this shape stays under the $5 budget

    Raw files

    S3 — …-raw

    Nightly extracts as they arrived — each file is a delta (new and changed rows), kept 7 days then lifecycle-expired. The renamed column is visible in the file itself, which is what makes the incident reproducible.

    s3://…/raw/dt=2026-11-18/customers.csv

    Analytics + RAG

    PostgreSQL + pgvector

    customers (live), customers_test (sandbox), customers_prev (kept after a swap, for rollback), applied_approvals (one row per used approval — what makes it single-use) and documents (runbook + contract chunks, vector(1024)) in one database. Docker on the Mac in Phases 1–7, RDS for the Phase 8 demo day only.

    How RAG flows: Diagnoser asks → MCP search_runbook embeds the question → pgvector returns the nearest chunks → Diagnoser answers citing them. No chunk, no claim.

    Memory

    DynamoDB — apa-memory

    Short-term: this run's findings. Long-term: past incidents and fixes — e.g. September's rename, where the fix was update the mapping, don't rebuild. Agents reach it only through the MCP tools save_note and recall_lessons. It holds no approvals.

    Approvals

    DynamoDB — apa-approvals

    A separate table in a separate trust boundary. Only the approve endpoint can write to it; agent roles and the memory client cannot. swap_tables() only reads it and refuses unless a record matches this incident and this test copy, is unexpired, and is not yet in the applied_approvals ledger.

    🛡️

    Guardrails are code, not a prompt

    The Fixer's first idea — rebuild live from S3 — would trade 3 years for 7 days. Three layers refuse it independently: a client-side hook, the tool server (which knows which agent is calling), and the Postgres role the Fixer connects with. In the build, Phase 4 forces this attempt rather than waiting for the model to try it.

    🧪

    Sandbox, then check, then ask

    The fix is built in customers_test — a clone of live plus tonight's file. The Verifier runs its 4 checks on the test copy first, before they ever run on live, and the result goes in the approval email. Only a test copy that passes can request approval.

    ✋

    Approval is enforced by the tool — and reversible

    swap_tables() checks apa-approvals itself, in a store no agent can write. If nobody approves, the wait times out and live is untouched. The swap is one atomic rename that keeps customers_prev, so a failed post-swap check is rolled back by the Fixer.

    Where it runs

    On your Mac while you build, in AWS for one demo day

    Phases 1–7 • your Mac

    Code local, orchestration in the cloud

    The pipeline job, the agents, the MCP tool servers and the publisher run on your Mac with uv, against Postgres in Docker. Step Functions and EventBridge are real AWS from the start: a small worker on the Mac polls Step Functions Activities for work and only dials out, so there is no open port and no tunnel (ADR-012). Everything the Mac does in AWS runs as the scoped kazi-dev-apa role, never an admin profile.

    Phase 8 • one demo day

    The same handlers, as Lambdas

    The worker's four tasks become Lambda invokes, Postgres moves to RDS, and a NAT gateway lets the Lambdas reach Bedrock. All of it sits behind one EnableDemo switch: on in dev for the recorded demo, off again the same day. Prod never gets RDS or a NAT gateway.

    How it ships • the platform you already built

    One project in your aws-data-platform repo

    Pull request→ Lint + Guard rules→ Preview dev + prod (read-only OIDC)→ Squash merge→ Deploy apa: dev, then prod after your approval

    The project lives in projects/apa/, with one stack folder per phase and its own deploy-apa.yml; stacks are named kazi-<env>-apa-<name>. The pipeline packages Lambda code into the platform's artifacts bucket, and a stack may create a role only if it carries the platform's permissions boundary. Each new AWS service is added to the pipeline's service role first, in its own reviewed change that you deploy by hand. Every incident leaves one trace in CloudWatch + X-Ray, replayable end to end.
