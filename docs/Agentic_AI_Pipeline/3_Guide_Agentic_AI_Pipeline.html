How to use this guide

The learning loop, every sitting: (1) read the phase's “idea” first; (2) do one step at a time, in order; (3) check the “you should see” box before moving on — if it doesn't match, stop and fix it there; (4) at the end of the phase, run the “check yourself” list. A phase is done when its checks pass, not when you feel done.

One sitting, one visible result. At 2–3 hours a week, a phase is 2–6 sittings. If a sitting ends with nothing working, the step is too big — split it.

Conventions. Commands you type start with $ and run in your Mac terminal (zsh). Run them from the project folder, ~/dev/aws-data-platform/projects/apa/, unless a step says repo root (~/dev/aws-data-platform). ap-southeast-2 is the region everywhere — if a console page shows another region, switch it first. Never paste AWS keys, passwords or tokens into the repo, a chat or a screenshot.

Three AWS profiles, three jobs. kazi-dev-admin is the human administrator: it deploys platform changes and runs one-off checks — never agent code. kazi-dev-apa (created in Phase 0, step 11) is the scoped runtime profile the Mac uses for everything the system does: Bedrock, S3, DynamoDB, Step Functions. kazi-dev-readonly is for looking. The SSO session for admin lasts 1 hour — when you see ExpiredToken, run aws sso login --sso-session kazi.

Names. Every AWS resource is called kazi-<env>-apa-…: the pipeline’s service role may only create names that start kazi-<env>-, and the apa part keeps this project’s resources apart from other projects’. The plan's short names map like this: apa-memory is the table kazi-<env>-apa-memory, apa-approvals is kazi-<env>-apa-approvals. Code reads these names from environment variables, never hard-codes them.

The one rule that matters most

Never let an agent — or a guide — do something you can't explain back in one sentence. If a step works but you don't know why, stop and re-read the “why” box. The portfolio is the understanding, not the repo.

How a change reaches AWS

One road to AWS: branch, pull request, preview, merge, deploy

One road, one exception. Every change goes through a pull request; a merge deploys to dev at once and to prod after you approve. When a phase needs a new AWS service, you widen the service role first — its own pull request, deployed by hand — and only then send the stack change down the same road.

Every change follows one road: branch → pull request → checks → squash merge → Deploy apa. The checks are Lint and policy scan (cfn-lint, the Guard rules, actionlint, zizmor, shellcheck and the script tests) and Preview dev and Preview prod, which create change sets for each project the pull request touches. Merging runs this project’s own workflow, Deploy apa: dev deploys automatically, prod after you approve it in the GitHub Environment. main is protected: a direct git push to it is refused, so every commit goes through a branch named feature/<short-description> and a pull request (one logical change each; squash-merge, because history must stay linear). There is no dev-only switch — a merged change deploys to prod too, after your approval.

What starts a deploy. Deploy apa runs when a merge touches projects/apa/, except Markdown files and projects/apa/docs/. That includes Python-only changes: the stacks then report no changes, and you approve the prod step anyway — it changes nothing. A merge that only touches Markdown or projects/apa/docs/ deploys nothing. You can also run it by hand: Actions → Deploy apa → Run workflow.

Platform changes are the exception. The pipeline cannot change its own permissions, by design. When a phase needs a new AWS service, you widen the service role in bootstrap/workload/pipeline-identity.yml through its own pull request — merging it deploys nothing — and then deploy it by hand in dev and prod (setup guide §9.5). It is still a reviewed CloudFormation deployment, never an ad-hoc console change. Phase 5 makes one platform change of another kind: if you run the evals in CI, they get a role of their own (setup guide §9.6), and the plan role is never widened.

What Preview does and does not prove. Preview creates a change set; it checks the template and the names, not whether the service role is allowed to create each resource. A missing permission shows up at deploy time as an AccessDenied event, and a failed first deploy leaves the stack in ROLLBACK_COMPLETE — which you must delete by hand (setup guide §11.2) before retrying. So “widen first, then add the stack” is a discipline you keep, not something CI enforces.

The widening procedure (same every time)

1. Find the permissions CloudFormation needs for the new resource type (setup guide §9.5.1).

2. On a branch, add one statement per service to the service role’s stack-resources policy in bootstrap/workload/pipeline-identity.yml, scoped to kazi-<env>-* names; the table below gives each phase’s starting statement. Nothing else goes in this pull request.

3. From the repo root, check it with uv run cfn-lint bootstrap/workload/pipeline-identity.yml, open the pull request and merge it.

4. Deploy it by hand, dev first, from an up-to-date main. Only then open the phase’s stack pull request.

The GitHubSubjectPrefix is your repository’s numeric identity, the value you deployed in the setup guide; a wrong one breaks the pipeline’s sign-in. Scoping rules for every new statement:

  • Never * to clear an error.
  • One statement per service, with a Sid that says what it is for, and resources scoped to kazi-<env>-* names, for example …:function:kazi-<env>-* or …:table/kazi-<env>-*. The pipeline’s own roles are named kazi-github-… and kazi-cfn-…, so they never match kazi-<env>-*.
  • A few read-only actions only work on *: give each its own statement, with a Sid that says why.
  • IAM needs no widening: the platform already lets stacks create roles named kazi-<env>-… that carry the permissions boundary, and refuses any other role.
  • EC2 cannot be scoped by name; scope its create calls by a request-tag condition instead (the pipeline tags every stack Project=apa and ManagedBy=cloudformation).
  • The statements below are the starting set: if a deploy event names one more action, add it the same way.

3Create the Detector with a 2-tool allow-list

The Detector physically cannot call a tool that isn't allowed — that is a design decision, not a request in the prompt. With MCP tools, the allow-list is the tool_filters argument of the client.

1. Write src/agents/detector.py:

In Strands an agent is a model plus tools plus a system prompt. The MCP client starts your server as a subprocess, and the tools are only valid while the client is open:

from strands import Agent
from strands.models import BedrockModel
from strands.tools.mcp import MCPClient
from mcp import StdioServerParameters
from mcp.client.stdio import stdio_client

model = BedrockModel(model_id="amazon.nova-micro-v1:0", region_name="ap-southeast-2")

logs = MCPClient(
    lambda: stdio_client(StdioServerParameters(
        command="uv", args=["run", "python", "-m", "src.tools.logs_server"],
        env={"AWS_PROFILE": "kazi-dev-apa", "DATABASE_URL": "..."},  # see note below
    )),
    tool_filters={"allowed": ["read_job_logs", "get_table_schema"]},
)

def main():
    with logs:
        tools = logs.list_tools_sync()
        detector = Agent(model=model, tools=tools,
                         system_prompt="You are the Detector. Find what broke in the failed run. "
                                       "Use only your tools. Cite the tool result for every claim.")
        print(detector("Run 2026-11-18-0214 failed. What broke?"))

if __name__ == "__main__":
    main()

The idea

The most important phase. The Fixer can repair the table — and it cannot destroy it. The idea

Until now, “it works” has meant “I watched it work once”. That doesn't survive change. A change that breaks the evals doesn't ship — and you can say, with numbers, whether a change helped or hurt.

“Looks good” is an opinion. Each check catches a different failure (partial load, wrong mapping, invalid status, corrupt data). Writing them is deciding what “fixed” means.

Checking only after the swap means live is already wrong when a check fails. Checking the copy first means the human only approves something already proven good, and the live check is the final net with a rollback behind it.

Phase 6 · 2 weeks · < $1

The Orchestrator: four specialists become a team

The idea

So far you have four agents that work alone. from pydantic import BaseModel, Field

class Evidence(BaseModel):
    claim: str
    source: str            # which tool result / runbook chunk / lesson

    next: str

Logs are a pile of lines; a trace is a story with a shape. When something fails at 2am you want one trace, not a grep — and span timings show exactly where the minutes went.

2Teach the pipeline to install Python dependencies (a platform change)

Until now every Lambda was plain Python. The Phase 8 functions import Strands, FastMCP, psycopg and pydantic, which the Lambda runtime does not have, and the pipeline’s packaging step only zips what is already in a folder. So the pipeline needs one more step: run the project’s own build.sh before it packages anything. The rule for it: install before any AWS credentials exist, wheels only, from the reviewed lockfile.

1. Write projects/apa/build.sh:

#!/usr/bin/env bash
# Fill build/lambda/ with the locked dependencies and the code, for Lambda.
# Runs in CI before any AWS credentials exist. Wheels only: no package code runs here.
set -euo pipefail
cd "$(dirname "$0")"
rm -rf build/lambda
mkdir -p build/lambda
uv export --frozen --no-dev --no-emit-project --format requirements-txt > build/requirements.txt
uv pip install --target build/lambda --python-version 3.13 --python-platform x86_64-manylinux2014 \
  --only-binary :all: --require-hashes -r build/requirements.txt
cp -R src build/lambda/

Point each Phase 8 function’s Code at ../../build/lambda, with the same W3002 note as the hello Lambda and handlers such as src.pipeline.load.handler. Try it on your Mac first: bash build.sh && ls build/lambda should list the packages and src.

2. Run it in both workflows, before the credentials step:

In .github/workflows/deploy-project.yml, add these two steps just before Assume the deploy role:

      - name: Set up uv
        uses: astral-sh/setup-uv@<same SHA as in pr-validate.yml>
        with:
          enable-cache: false   # no shared cache in a job that later holds AWS credentials

      - name: Build project code (no AWS credentials yet)
        env:
          PROJECT: ${{ inputs.project }}
        run: |
          if [ -f "projects/$PROJECT/build.sh" ]; then bash "projects/$PROJECT/build.sh"; fi

In .github/workflows/pr-validate.yml, add the same Set up uv step and this build step to the preview job, just before Assume the plan role. It builds every project the pull request touches:

      - name: Build project code (no AWS credentials yet)
        env:
          BASE_REF: origin/${{ github.base_ref }}
        run: |
          for project in $(./scripts/changed-projects.sh "$BASE_REF"); do
            if [ -f "projects/$project/build.sh" ]; then bash "projects/$project/build.sh"; fi
          done

3. Check the workflows, then ship this as its own pull request:

$ actionlint; echo "actionlint exit=$?"

expect actionlint exit=0 and No findings to report. The pull request changes .github/, so it previews every project; merging runs each project’s deploy once, which changes nothing

Why build before credentials

The build downloads code written by strangers. Installing wheels only, checked against the hashes in your lockfile, means none of that code runs during the install; doing it before the credentials step means even a bad package has nothing to steal. A project without a build.sh, such as sample, skips the step.

Appendix A

When you're stuck

Read the error, all of it. Most errors name the problem in the last two lines. Copy the message into your notes before you fix anything.

Bisect. If something worked and now doesn't, find the last change and undo it. If a step fails, re-run the step before it to learn whether the problem is here or upstream.

Check the account, region and session first. aws sts get-caller-identity and the console region. ExpiredToken means the 1-hour admin session ended: aws sso login --sso-session kazi.

“Explicit deny in a service control policy” means a guardrail, not a missing permission: you tried a region other than Sydney or N. Virginia — often a Bedrock cross-region profile.

A deploy failed after Preview passed. Preview doesn't test the service role. Read the failed event in the stack's Events tab; a missing action means widening the service role (the procedure at the top). A first-time failure leaves ROLLBACK_COMPLETE: delete the stack with the admin profile, then redeploy (setup guide §11.2).

Everything is denied, even simple reads. The budget brake may be attached: the month’s spend reached $5. Follow setup guide §11.3 to see why and to release it.

Ask the plan. Re-read the relevant ADR — it usually names the fallback. Bring the exact error, not a summary of it.

Take the win. If a sitting ends with one small thing working that didn't before, that was a good sitting. Write down what changed.
