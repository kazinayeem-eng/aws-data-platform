Start here

When you finish this guide, you can open a pull request, see exactly what it would change in AWS, merge it, and watch it deploy to a dev account and then, after one approval from you, to a prod account. Each project in the repository deploys on its own, spending stops at $5 a month, and no AWS password or access key is stored anywhere.

Why build it this way The usual shortcut is to create resources by hand in the AWS console and keep an access key in your CI system. That works until someone mistypes a setting in production, or a leaked key gives a stranger permanent access. This setup removes both problems: every change is written down, checked and previewed before it runs, and every sign-in is temporary and tied to one exact repository.

Example You need a new S3 bucket. You add it to a project's template, open a pull request, read the preview that says "this will add one bucket", merge, and approve the prod deployment. Nobody clicks in the console and nobody holds a key.

1. The design in one page

Why this section Before you build anything, it helps to know what the finished system looks like and why it is shaped that way. Each piece stops one specific kind of mistake or attack, and the later steps make more sense once you know which piece each one builds.

Example Dev and prod are separate AWS accounts. If you break something while experimenting in dev, there is no route by which that mistake can delete production data.

1.1What you will have

  • An AWS Organization with three accounts: management, dev and prod.
  • Human sign-in through IAM Identity Center (single sign-on) with a second factor. No IAM users and no access keys.
  • A public GitHub repository where main is protected and only a merged pull request can reach AWS.
  • One folder per project. A pull request previews only the projects it touches, and a merge deploys only those projects.
  • Pull requests that check your templates, workflows and scripts, and show the exact change they would make before anyone merges.
  • Merges that deploy to dev automatically, and to prod only after you approve.
  • Pipeline roles split by account and by purpose. Any IAM role a project creates is capped by a permissions boundary.
  • A $5 monthly budget with alerts and an automatic brake that freezes dev and prod when the budget is spent.
  • An audit trail, decisions and runbooks kept in the repository, and a page of fixes for the failures you are likely to meet.

1.2Three accounts, so a mistake stays small

An AWS account is a hard boundary. One Organization holds three of them. The management account only runs the organization: sign-in, billing, the budget and the audit trail. Dev and prod each sit in their own group of accounts, called an organizational unit (OU). Guardrails called service control policies (SCPs) are attached to those groups and limit what anyone can do inside them, administrators included.

1.3Two kinds of change, two routes

Platform changes are the guardrails, the budget brake and the pipeline's own permissions. You make these yourself, rarely and carefully, from a signed-in administrator session. Workload changes are everything else, such as a new bucket in a project. Only the pipeline makes these, and each one passes the two gates in the picture at the top of this page before it reaches prod.

Even for workloads, GitHub never gets permission to create resources itself. It can only ask CloudFormation to do the work, and a separate service role inside each account does the creating. So even a hijacked pipeline cannot build or change anything beyond what the templates describe.

1.4One repository, many projects

Each project lives in its own folder under projects/, and its CloudFormation stacks live in numbered folders inside it. A project's code, tests and docs sit beside its stacks, so everything about one project is in one place. Each project also has its own small deploy workflow, so merging a change to one project never redeploys another.

A stack's name comes from its folder, so you never choose it by hand. The project is part of the name, so two projects can both have a stack folder called 00-bucket:

1.5The choices behind the design

Question Our answer Why
How many accounts? Management, dev and prod Each environment gets its own limits, billing and blast radius
How do people sign in? IAM Identity Center with MFA Sessions expire in hours and there are no keys to leak
How does GitHub sign in? OpenID Connect (OIDC), one role per purpose No stored secret, and each role trusts only one exact kind of job
How is infrastructure written? CloudFormation AWS-native, no state file to protect, and change sets preview every change
Who creates the resources? A CloudFormation service role GitHub's own credentials cannot create anything directly
What stops a template creating an admin role? A permissions boundary on every role a stack creates The pipeline can never give anything more access than the boundary allows
How is a deploy run? Scripts in the repository, tested on every pull request You can read them end to end, and no third party touches credentials
How are projects kept apart? One folder and one deploy workflow per project A change or a failure in one project never touches another
How do you see a change first? A change set on every pull request AWS itself reports what would change
How does a change reach prod? The same commit goes to dev, then to prod after approval What you tested is what ships
How are templates checked? cfn-lint for correctness, cfn-guard rules for policy Both run in CI and block a merge when they fail
How are Python tools installed? uv, from one lockfile Your Mac and the pipeline install the same version of every package
How is spending capped? A $5 budget with alerts and an automatic brake AWS has no hard cap, so the brake freezes dev and prod at $5

Some things are left out on purpose. More accounts (for logs or experiments) were considered and declined: three is enough. GuardDuty, AWS Config and Security Hub bill by usage and are left for later. AWS Control Tower builds a similar foundation automatically, but turns on AWS Config, which bills per recorded change. Terraform and CDK are other ways to write infrastructure; the account and sign-in design would carry over unchanged.

The repository keeps these choices in docs/decisions.md, so they live next to the code they explain.

1.6What it costs, and how a surprise bill is stopped

Following this guide should cost close to nothing. The figures come from the vendors' published pricing.

Item Expected cost
GitHub Free with a public repository, including Actions on standard runners USD 0
AWS Organizations, IAM Identity Center, IAM roles and SCPs USD 0
CloudFormation with ordinary AWS resources such as S3 USD 0
Organization CloudTrail (management events only) USD 0 for the trail; the log files cost cents a month
IAM Access Analyzer (external access) and S3 Block Public Access USD 0
AWS Budgets, including one budget with an action, and Cost Anomaly Detection USD 0 (the first two budgets with actions are free)
The artifacts buckets and the data buckets, while nearly empty Cents a month at most

AWS has no hard spending cap, so this guide sets up three layers of protection:

  1. Alerts. A $5 monthly budget emails you at 50%, 80% and 100% of actual spend, and when the forecast passes 100%. A separate alert emails you when daily spend looks unusual.
  2. An automatic brake. At $5 of actual spend, AWS Budgets attaches a guardrail that freezes the dev and prod accounts. You can still sign in and clean up.
  3. Nothing open-ended by default. No NAT gateways, customer-managed KMS keys, always-on databases or usage-billed security services.

Two limits to know. Billing data reaches AWS Budgets hours after the spend, so the brake can fire after spend has passed $5. And the brake stops new spending, not charges for resources that are already running: you still delete those yourself.

4. Build the AWS foundation

Why this section Everything else sits on top of this. You create the three accounts, a safe way for you to sign in, spending alerts and an audit log. Doing it carefully once means you never need a shared password, an access key, or a surprise bill.

Write the policy rules

Every template in this repository must pass these rules, and the pipeline enforces them on every pull request. Save this as guard/s3-baseline.guard:

guard/s3-baseline.guard
# Rules every S3 bucket in this repository must follow. CI checks every
# template with them; run them yourself with:
#   cfn-guard validate --rules guard/ --data <template.yml>
let buckets = Resources.*[ Type == 'AWS::S3::Bucket' ]

rule s3_buckets_are_encrypted when %buckets !empty {
    %buckets.Properties.BucketEncryption exists
}

rule s3_buckets_block_public_access when %buckets !empty {
    %buckets.Properties.PublicAccessBlockConfiguration.BlockPublicAcls == true
    %buckets.Properties.PublicAccessBlockConfiguration.BlockPublicPolicy == true
    %buckets.Properties.PublicAccessBlockConfiguration.IgnorePublicAcls == true
    %buckets.Properties.PublicAccessBlockConfiguration.RestrictPublicBuckets == true
}

# Deleting a stack may delete its buckets (decision D13), but a change that
# replaces a bucket, such as a rename, must never delete the old one with it.
rule s3_buckets_survive_replacement when %buckets !empty {
    %buckets.UpdateReplacePolicy == 'Retain'
}

5.2Deploy the guardrails and the budget brake

This template holds two guardrails (SCPs) for the dev and prod accounts and the budget brake. Guardrails apply to everyone in those accounts, administrators included. They never apply to the management account.

Part What it does
DenyRootUser Blocks any use of the root user inside dev and prod
DenyLeavingOrganization Stops an account detaching itself from your guardrails
ProtectSecurityControls Blocks switching off CloudTrail, deleting Access Analyzer, or loosening account-level S3 Block Public Access
DenyUnapprovedRegions Blocks every Region except <region> and us-east-1. Global services such as IAM, Route 53 and CloudFront stay usable
Budget brake A second guardrail, attached to nothing until spend reaches $5. AWS Budgets then attaches it to dev and prod by itself. It denies everything except you (signed in through SSO) and the CloudFormation service role, so you can still clean up
5.2.1Editor

Create the guardrails template

  • BudgetBrake is the guardrail itself. Its one rule denies every action, except for roles created by Identity Center (that is you) and the CloudFormation service role (so delete-stack still works).
  • BudgetBrakeRole can be used only by AWS Budgets, for a budget in this account, and can only attach and detach guardrails.
  • BudgetBrakeAction watches the <org>-monthly budget you created in section 4. When actual spend reaches 100%, it attaches the brake to the dev and prod accounts automatically and emails you.

5.3Deploy the pipeline identity

One template, deployed once into each workload account, creates everything the pipeline needs:

Resource Purpose Who or what can use it
GitHub OIDC provider Tells the account to trust tokens issued by GitHub Actions It is the trust anchor, not a role
<org>-github-plan-<env> Previews change sets on pull requests; cannot execute anything Only a pull request in your repository
<org>-github-deploy-<env> Executes change sets after a merge Only a job that targets the matching GitHub Environment
<org>-cfn-service-<env> Holds the permission to create resources Only the CloudFormation service
<org>-<env>-artifacts-... bucket Holds packaged code, such as Lambda zips, uploaded during previews and deploys The plan and deploy roles write; CloudFormation reads
<org>-workload-boundary-<env> The permissions boundary every role created by a stack must carry Attached to roles; nobody uses it directly

Today the service role can create only S3 buckets, and IAM roles that carry the boundary. When a project needs another AWS service, you widen it deliberately, one service at a time.

5.3.1Editor

Create the pipeline identity template

  • The GitHub roles can ask CloudFormation for changes and pass it the service role, nothing more. Both may also tag stacks, because CloudFormation checks cloudformation:TagResource when a change set carries tags, and the deploy script always adds them.
  • The service role may create IAM roles only if they are named <org>-<env>-* and carry the boundary. Without that condition, any template could create an administrator.
  • The boundary allows everything except changes to identities (iam:*), the organization, the account and single sign-on. A role created by a stack can never grant itself more.
  • The artifacts bucket is encrypted, private, versioned and kept if the stack is deleted. Packages expire after 90 days.

5.4How the trust works

This is what makes "no stored keys" safe, and why a different repository, a fork or a stray branch cannot deploy to your accounts. When a workflow runs, GitHub issues a signed token whose subject (sub) claim describes exactly what is running. AWS compares that claim with the role's trust policy, and each role trusts exactly one claim, with no wildcards.

Suppose a stranger forks your public repository and opens a pull request. Their job gets a token from GitHub, but its subject names their repository, not yours, so AWS refuses it. Your <subject-prefix> carries the numeric owner and repository IDs, so even someone who later takes over your old repository name cannot match it.

Because the deploy role is reachable only through a GitHub Environment, the rules you set on that Environment in section 6, such as your approval and the restriction to main, are enforced by AWS as well as by GitHub.

The two thumbprints in the template are a fallback: AWS checks GitHub's certificate against its own trusted authorities first, but the resource requires at least one thumbprint.

Create scripts/cfn-change.sh

  • Builds the stack name from the folder: projects/<project>/stacks/NN-name becomes <org>-<env>-<project>-<name>. A folder anywhere else, or with characters a stack name cannot hold, is refused.
  • name mode prints that name and stops before anything needs AWS, so you can test the rule on your Mac.

  • Preview writes a table of the changes to the job summary, warns if anything would be removed or replaced, then deletes the change set. Apply executes it, waits, and prints the failed events if it fails. It does not turn on termination protection, so a stack can always be deleted (decision D13).

#!/usr/bin/env bash
# Preview or apply one CloudFormation stack through a change set.
#
#   scripts/cfn-change.sh preview|apply <stack-dir> <environment>
#   scripts/cfn-change.sh name <stack-dir> <environment>   (prints the stack name and stops)
#
# <stack-dir> must look like projects/<project>/stacks/<NN-name>. The stack is
# named <ORG_PREFIX>-<environment>-<project>-<name>, so two projects can both
# have a stack folder called 00-bucket without colliding.
#
# Every mode needs ORG_PREFIX (for example: acme). preview and apply also need
# AWS credentials and a Region in the environment, and CFN_ROLE_ARN, the
# CloudFormation service role that creates the resources.
set -euo pipefail

mode="${1:?usage: cfn-change.sh preview|apply|name <stack-dir> <environment>}"
stack_dir="${2:?missing stack directory}"
env_name="${3:?missing environment}"
: "${ORG_PREFIX:?ORG_PREFIX is not set}"

case "$mode" in
  preview|apply|name) ;;
  *) echo "mode must be 'preview', 'apply' or 'name'" >&2; exit 2 ;;
esac
case "$env_name" in
  dev|prod) ;;
  *) echo "environment must be 'dev' or 'prod', got: $env_name" >&2; exit 2 ;;
esac

# The folder decides the stack name: projects/<project>/stacks/<NN->name.
stack_dir="${stack_dir%/}"
folder_pattern='^(\./)?projects/([a-z][a-z0-9-]{1,19})/stacks/([0-9]+-)?([a-z][a-z0-9-]*)$'
if [[ ! "$stack_dir" =~ $folder_pattern ]]; then
  echo "Stack folder must look like projects/<project>/stacks/<NN-name>, in lower-case letters, digits and hyphens. Got: $stack_dir" >&2
  exit 2
fi
project="${BASH_REMATCH[2]}"
stack_name="${ORG_PREFIX}-${env_name}-${project}-${BASH_REMATCH[4]}"
if [[ "$mode" == name ]]; then
  echo "$stack_name"
  exit 0
fi

: "${CFN_ROLE_ARN:?CFN_ROLE_ARN is not set}"
region="${AWS_REGION:-${AWS_DEFAULT_REGION:-}}"
: "${region:?AWS_REGION is not set}"
template="${stack_dir}/template.yml"
params="${stack_dir}/${env_name}.json"
change_set="${mode}-${GITHUB_SHA:-local}-$(date +%s)"
summary="${GITHUB_STEP_SUMMARY:-/dev/stdout}"

if [[ ! -f "$template" || ! -f "$params" ]]; then
  echo "Missing $template or $params" >&2
  exit 1
fi

# Upload any local code the template points at (such as a Lambda function's
# CodeUri) to this account's artifacts bucket. A template without local code
# comes out unchanged.
account="$(aws sts get-caller-identity --query Account --output text)"
packaged="$(mktemp)"
trap 'rm -f "$packaged"' EXIT
aws cloudformation package \
  --template-file "$template" \
  --s3-bucket "${ORG_PREFIX}-${env_name}-artifacts-${account}-${region}" \
  --s3-prefix "$project" \
  --output-template-file "$packaged" > /dev/null

# A stack that does not exist yet, or only exists as an empty preview shell,
# needs a CREATE change set. A stuck ROLLBACK_COMPLETE stack must be deleted first.
status="$(aws cloudformation describe-stacks --stack-name "$stack_name" \
  --query 'Stacks[0].StackStatus' --output text 2>/dev/null || echo NONE)"
case "$status" in
  NONE|REVIEW_IN_PROGRESS) cs_type=CREATE ;;
  ROLLBACK_COMPLETE)
    echo "Stack $stack_name is in ROLLBACK_COMPLETE and must be deleted first (see the runbook for a failed deployment)." >&2
    exit 1 ;;
  *) cs_type=UPDATE ;;
esac

aws cloudformation create-change-set \
  --stack-name "$stack_name" \
  --change-set-name "$change_set" \
  --change-set-type "$cs_type" \
  --template-body "file://${packaged}" \
  --parameters "file://${params}" \
  --role-arn "$CFN_ROLE_ARN" \
  --capabilities CAPABILITY_NAMED_IAM \
  --tags "Key=Environment,Value=${env_name}" \
         "Key=Project,Value=${project}" \
         "Key=ManagedBy,Value=cloudformation" \
         "Key=Repository,Value=${GITHUB_REPOSITORY:-local}" \
  --query Id --output text > /dev/null

if ! aws cloudformation wait change-set-create-complete \
    --stack-name "$stack_name" --change-set-name "$change_set" 2>/dev/null; then
  reason="$(aws cloudformation describe-change-set \
    --stack-name "$stack_name" --change-set-name "$change_set" \
    --query StatusReason --output text)"
  if [[ "$reason" == *"didn't contain changes"* || "$reason" == *"No updates are to be performed"* ]]; then
    echo "### ${stack_name}: no changes" >> "$summary"
    aws cloudformation delete-change-set --stack-name "$stack_name" --change-set-name "$change_set"
    exit 0
  fi
  echo "Change set for $stack_name failed: $reason" >&2
  exit 1
fi

details="$(aws cloudformation describe-change-set \
  --stack-name "$stack_name" --change-set-name "$change_set" --output json)"

{
  echo "### ${stack_name} (${cs_type})"
  echo
  echo "| Action | Logical ID | Type | Replacement |"
  echo "|---|---|---|---|"
  jq -r '.Changes[].ResourceChange
         | "| \(.Action) | \(.LogicalResourceId) | \(.ResourceType) | \(.Replacement // "-") |"' <<< "$details"
  echo
  if jq -e '[.Changes[].ResourceChange
             | select(.Action == "Remove" or .Replacement == "True" or .Replacement == "Conditional")]
            | length > 0' <<< "$details" > /dev/null; then
    echo "> **Warning:** this change removes or replaces at least one resource. Check DeletionPolicy and data impact before merging."
    echo
  fi
} >> "$summary"

if [[ "$mode" == preview ]]; then
  aws cloudformation delete-change-set --stack-name "$stack_name" --change-set-name "$change_set"
  exit 0
fi

aws cloudformation execute-change-set --stack-name "$stack_name" --change-set-name "$change_set"

if [[ "$cs_type" == CREATE ]]; then waiter=stack-create-complete; else waiter=stack-update-complete; fi
if ! aws cloudformation wait "$waiter" --stack-name "$stack_name"; then
  echo "Deployment of $stack_name failed. Failed events:" >&2
  aws cloudformation describe-stack-events --stack-name "$stack_name" --max-items 50 \
    --query "StackEvents[?contains(ResourceStatus, 'FAILED')].[LogicalResourceId,ResourceStatus,ResourceStatusReason]" \
    --output table >&2
  exit 1
fi

# No termination protection: deleting a stack, from the console or the CLI,
# removes everything in it (decision D13).
echo "Deployed ${stack_name}"

#
#   scripts/cfn-project.sh preview|apply <project> <environment> [--only <folder>] [--skip <folder>]
#
# Stacks live in projects/<project>/stacks/<NN-name>/ and run in name order, so
# 00-foundation goes before 01-pipeline. A folder without a template.yml is skipped.
# Needs the same environment variables as scripts/cfn-change.sh.

env_name="${3:?missing environment}"
shift 3

only=""
skip=""
while [[ $# -gt 0 ]]; do
  case "$1" in
    --only) only="${2:?--only needs a stack folder name}"; shift 2 ;;
    --skip) skip="${2:?--skip needs a stack folder name}"; shift 2 ;;
    *) echo "unknown option: $1" >&2; exit 2 ;;
  esac
done

case "$mode" in
  preview|apply) ;;
  *) echo "mode must be 'preview' or 'apply'" >&2; exit 2 ;;
esac

  exit 2
fi

if [[ ! -d "$root" ]]; then
  echo "No such project: $root does not exist" >&2
  exit 1
fi

shopt -s nullglob
count=0

  if [[ ! -f "${dir}template.yml" ]]; then
    echo "skip ${dir}: no template.yml"
    continue
  fi
  if [[ -n "$only" && "$name" != "$only" ]]; then continue; fi
  if [[ -n "$skip" && "$name" == "$skip" ]]; then continue; fi
  count=$((count + 1))
  ./scripts/cfn-change.sh "$mode" "$dir" "$env_name"
done

echo "${mode}: ${count} stack(s) in project ${project}"

Create scripts/changed-projects.sh

  • Ignores Markdown files, so a docs edit never needs a preview.
  • Treats a change under scripts/, bootstrap/ or .github/ as affecting every project.

#!/usr/bin/env bash
# Print the projects a pull request needs to preview, one per line.
#
#   scripts/changed-projects.sh <base-ref>        (for example: origin/main)
#
# A change to shared pipeline files (scripts/, bootstrap/, .github/) means every
# project. Markdown files are ignored. A project without a stacks/ folder (for
# example one you have just deleted) is never listed.
set -euo pipefail

base="${1:?usage: changed-projects.sh <base-ref>}"
# Kept on its own line so a missing base ref stops the script instead of
# quietly reporting "no changes".
diff="$(git diff --name-only "${base}...HEAD")"
changed="$(printf '%s\n' "$diff" | grep -vE '\.md$' || true)"

if printf '%s\n' "$changed" | grep -qE '^(scripts/|bootstrap/|\.github/)'; then
  names="$(find projects -mindepth 1 -maxdepth 1 -type d -exec basename {} \; 2>/dev/null || true)"
else
  names="$(printf '%s\n' "$changed" | sed -nE 's#^projects/([^/]+)/.*#\1#p')"
fi

printf '%s\n' "$names" | sort -u | while IFS= read -r name; do
  if [[ -n "$name" && -d "projects/${name}/stacks" ]]; then
    echo "$name"
  fi
done

# aws-data-platform

One repo, many projects, three AWS accounts. Each project has its own folder, its own stacks and its own deploy workflow. A pull request previews exactly what it would change in dev and prod; a merge deploys to dev, then to prod after one approval. No AWS keys are stored anywhere.

## Layout

```
projects/<project>/stacks/<NN-name>/     template.yml, dev.json, prod.json
projects/<project>/                      code, tests and docs for that project
.github/workflows/deploy-<project>.yml   one deploy workflow per project
.github/workflows/deploy-project.yml     shared deploy steps, called by the project workflows
.github/workflows/pr-validate.yml        lint, policy rules, tests and previews on every pull request
scripts/                                 the pipeline scripts
tests/pipeline-test.sh                   tests for the pipeline scripts
guard/                                   policy rules every template must pass
bootstrap/                               guardrails, budget brake and pipeline identity (deployed by hand)
docs/                                    decisions, accepted risks and runbooks
pyproject.toml, uv.lock                  the pinned Python tools; run them with uv run
```

## Names

A stack is named `<org>-<env>-<project>-<name>`, where `<name>` is the stack folder without its number: `projects/sample/stacks/00-bucket` becomes `acme-dev-sample-bucket`.

Name every resource a project creates `<org>-<env>-<project>-...` too. The pipeline's service role can only create resources whose names start with `<org>-<env>-`, so that part is required, not just tidy. IAM roles must also carry the permissions boundary `<org>-workload-boundary-<env>`.

## Add a project

1. Pick a short name: 2 to 20 lower-case letters, digits or hyphens, starting with a letter.
2. Create `projects/<project>/stacks/00-<name>/` with `template.yml`, `dev.json` and `prod.json`.
3. Copy the workflow and swap the name: `sed 's/sample/<project>/g' .github/workflows/deploy-sample.yml > .github/workflows/deploy-<project>.yml`
4. Check it: `uv run cfn-lint projects/<project>/stacks/*/template.yml` and `cfn-guard validate --rules guard/ --data <template>`.
5. Open a pull request. `Preview dev` and `Preview prod` show what will be created.
6. Merge. The new workflow deploys dev, then waits for your approval before prod.

If the project needs a resource type the service role cannot create yet, widen `bootstrap/workload/pipeline-identity.yml` in its own pull request first, then redeploy it by hand in dev and prod.

## Remove a project

1. Empty its buckets, then delete its stacks, in the console or with an admin profile. Deleting a stack removes everything in it, buckets included; a stack whose bucket is not empty stops at `DELETE_FAILED`, so empty the bucket and delete again.
2. In a pull request, delete `projects/<project>/` and `.github/workflows/deploy-<project>.yml`.

Deleting a stack folder never deletes the stack in AWS. That is always a deliberate, manual step.

## Rules

- `main` is protected. Every change is a branch, a pull request and a squash merge.
- No keys, passwords or tokens in the repo. The pipeline signs in with OIDC.
- Never widen a role to `*`.
- Never widen the plan role for tests. A project whose CI tests need AWS gets its own job and its own role (D14 in `docs/decisions.md`).
- Run `bash tests/pipeline-test.sh` after changing anything in `scripts/`.
- A change under `scripts/`, `bootstrap/` or `.github/` previews every project. A Markdown-only change previews and deploys nothing.
- If spend reaches the monthly budget, the budget brake freezes dev and prod until you release it. See `docs/runbooks.md`.

# Decisions

Each entry records one choice, why it was made, and when to look at it again.

## D1. Three AWS accounts in one organization

**Decision.** A management account, a dev account and a prod account. Dev and prod each sit in their own organizational unit, with guardrails (service control policies) attached.

**Why.** An account is a hard boundary, so a mistake in dev has no route into prod, and guardrails limit even administrators.

**Revisit when.** Never for the split. More accounts were considered and declined; add one only for a clear, lasting need.

## D2. People sign in with IAM Identity Center

**Decision.** Single sign-on with MFA for every person, with session lengths of 1 hour (admin) and 4 hours (read-only). No IAM users and no access keys.

**Why.** Sessions expire on their own, and there is nothing long-lived to leak.

## D3. GitHub signs in with OIDC, one role per purpose

**Decision.** In each workload account, a plan role for pull requests (preview only), a deploy role reachable only through a GitHub Environment, and a CloudFormation service role that alone creates resources. Each GitHub role trusts one exact token subject that includes the repository's numeric IDs.

**Why.** No stored secret, and a stolen or forged workflow cannot reach more than its one job allows.

## D4. CloudFormation with change sets, run by a script in the repository

**Decision.** Plain CloudFormation templates. `scripts/cfn-change.sh` previews and applies one stack through a change set.

**Why.** AWS-native, no state file to protect, and every change is previewed by AWS itself. A script you can read beats a third-party action that handles credentials.

**Revisit when.** Learning Terraform becomes the goal.

## D5. One repository, many projects

**Decision.** Each project lives in `projects/<project>/`, with stacks in `projects/<project>/stacks/<NN-name>/`, named `<org>-<env>-<project>-<name>`. Each project has its own deploy workflow; pull requests preview only the projects they touch.

**Why.** A change to one project never redeploys another, and a failed deploy in one project never blocks the others.

**Revisit when.** Projects need different owners or different permissions: then give them their own roles, or their own repository.

## D6. Roles created by stacks must carry a permissions boundary

**Decision.** The service role may create IAM roles only if they are named `<org>-<env>-*` and carry the boundary `<org>-workload-boundary-<env>`, which denies any change to identities, the organization or the account.

**Why.** Without it, any template could create an administrator role, and the pipeline would be administrator in all but name.

## D7. Code is packaged into an artifacts bucket in each account

**Decision.** `scripts/cfn-change.sh` runs `aws cloudformation package` before every change set, uploading local code to `<org>-<env>-artifacts-<account>-<region>`.

**Why.** A project with Lambda code deploys exactly like a project without it, with no special upload steps.

**Trade-off.** The plan role can write to that one bucket during pull request previews. Uploaded packages expire after 90 days.

## D8. Policy rules with cfn-guard, not checkov

**Decision.** Rules in `guard/` that every template must pass, enforced in CI from the first pull request.

**Why.** One small binary instead of about a hundred Python packages, and rules you wrote yourself and understand.

**Revisit when.** You want broad off-the-shelf checks: AWS publishes Guard rule sets that can be added to `guard/`.

## D9. Python tools pinned with uv

**Decision.** `pyproject.toml` and `uv.lock` pin cfn-lint and zizmor; CI installs them with `uv sync --locked`.

**Why.** Your Mac and the pipeline run exactly the same versions.

## D10. A $5 monthly cost ceiling with an automatic brake

**Decision.** A $5 budget alerts at 50%, 80% and 100% of actual spend and at 100% of forecast spend. At $5 of actual spend, a budget action attaches a guardrail that freezes the dev and prod accounts, except for people signed in through Identity Center and the CloudFormation service role.

**Why.** AWS has no hard spending cap. Alerts plus a brake make a surprise bill unlikely.

**Limits.** Billing data arrives with a delay of hours, and charges for resources that are already running continue until you delete them.

## D11. Not now: GuardDuty, AWS Config, Security Hub, a log archive account

**Why.** They add cost or accounts that a one-person learning platform does not need yet. They are recorded as accepted risks.

**Revisit when.** Real data or other people arrive.

## D12. A public repository with solo approvals

**Decision.** A public repository on GitHub Free, where you approve your own prod deployments.

**Why.** GitHub Free offers branch rulesets and required reviewers only on public repositories.

**Revisit when.** Before you add any collaborator.

## D13. Deleting a stack removes everything in it

**Decision.** Stacks have no termination protection, and buckets use `DeletionPolicy: Delete` and need no versioning. Deleting a stack, in the console or with the CLI, removes all of its resources once its buckets are empty. Buckets still use `UpdateReplacePolicy: Retain`, and the Guard rules check that.

**Why.** Teardown should be one deliberate delete, not a hunt for resources that were kept behind. You empty a bucket yourself first; a delete that meets a full bucket stops at `DELETE_FAILED`, and you retry it.

**Trade-off.** A deleted stack, or a bucket removed from a merged template, cannot be recovered, and there are no old object versions to restore. A change that replaces a bucket still keeps the old one.

**Revisit when.** A project holds data you cannot recreate.

## D14. A project's tests in CI: their own job and their own role

**Decision.** A project whose tests need more than the lint job, such as a database or a model on Bedrock, gets its own job in `.github/workflows/pr-validate.yml`. The job always runs: its first step asks `scripts/changed-projects.sh` whether its project changed, and if not, it skips its other steps and still ends green. Tests that need AWS sign in with their own role in `bootstrap/workload/pipeline-identity.yml`, in dev only and allowed only what they need. The plan role is never widened for tests.

**Why.** The plan role stays preview-only. A required check must report on every pull request, and a paths filter would leave it waiting for ever on the pull requests it skips. With one project that needs this, a job in the shared workflow is simpler than a hook.

## A failed deployment

Read the failing events first:

```sh
aws cloudformation describe-stack-events --stack-name <org>-<env>-<project>-<name> --query "StackEvents[?contains(ResourceStatus,'FAILED')].[LogicalResourceId,ResourceStatusReason]" --output table --profile <org>-<env>-readonly
```

| Status | What it means | What to do |
|---|---|---|
| `UPDATE_ROLLBACK_COMPLETE` | An update failed and was undone | The stack is healthy. Fix the cause in a new pull request |
| `ROLLBACK_COMPLETE` | The first creation failed, and the stack cannot be updated | Fix the cause, delete the stack with an admin profile, then use **Run workflow** on the project's workflow |
| `UPDATE_ROLLBACK_FAILED` | The rollback itself failed | Fix the cause, then run `aws cloudformation continue-update-rollback --stack-name <stack>` with an admin profile |
| `DELETE_FAILED` | A resource could not be deleted, often a bucket that is not empty | Empty or keep the resource, then retry |
| `REVIEW_IN_PROGRESS` | An empty shell left by a preview of a new stack | Harmless. The next deploy uses it |

A bucket that holds objects cannot be deleted, so a stack delete, or the rollback of a failed first deployment, can stop at `DELETE_FAILED`. Empty the bucket (S3 console → the bucket → **Empty**), then delete again.

## The budget brake fired

You get an email saying the budget action ran. Dev and prod are now frozen: previews, deploys and your workloads' own AWS calls fail with `explicit deny in a service control policy`. You can still sign in through Identity Center and clean up.

1. Find what costs money. In the management account, open **Billing and Cost Management → Cost Explorer**, group by **Service**, and look at the last 7 days.
2. Stop it. Delete or scale down the resource. To delete a whole stack, use the console or an admin profile: CloudFormation does the work with the service role, which the brake leaves alone. Empty its buckets first.

    ```sh
    aws cloudformation delete-stack --stack-name <stack> --profile <org>-<env>-admin
    ```

3. Release the brake from the management account. The first command prints the action ID and `EXECUTION_SUCCESS`; the second releases it:

    ```sh
    aws budgets describe-budget-actions-for-budget --account-id <mgmt-account-id> --budget-name <org>-monthly --query 'Actions[].[ActionId,Status]' --output text --region us-east-1 --profile <org>-mgmt-admin
    aws budgets execute-budget-action --account-id <mgmt-account-id> --budget-name <org>-monthly --action-id <action-id> --execution-type REVERSE_BUDGET_ACTION --region us-east-1 --profile <org>-mgmt-admin
    ```

4. A released brake stays off for the rest of the month. On the first day of the next month, run the first command again. It should print `STANDBY`; if it does not, re-arm the brake with `--execution-type RESET_BUDGET_ACTION`.

## Drift

Drift means something in AWS no longer matches its template, usually because someone changed it by hand.

```sh
aws cloudformation detect-stack-drift --stack-name <stack> --query StackDriftDetectionId --output text --profile <org>-<env>-admin
aws cloudformation describe-stack-resource-drifts --stack-name <stack> --stack-resource-drift-status-filters MODIFIED DELETED --profile <org>-<env>-admin
```

Wait about a minute between the two commands. Resolve every difference: put the real change into the template, or put the resource back.

## Break-glass: when the normal route is unavailable

Escalate only as far as you must, and clean up afterwards.

**Level 1: the pipeline is down or too slow.**

1. Sign in with `aws sso login --sso-session <org>`.
2. Make the smallest change that stops the harm.
3. Write down what, why and when.
4. Put the same change into code the same day.
5. Run drift detection, and review your session in CloudTrail.

**Level 2: Identity Center is down, or you are locked out.** A last resort. Read it now; do not rehearse it.

1. Sign in at `https://console.aws.amazon.com/` as the management root user, with its password and one MFA device from Bitwarden.
2. In IAM, create a temporary user named `breakglass-temp` with the `AdministratorAccess` policy and a console password.
3. Sign out, then sign in as `breakglass-temp`.
4. Switch role into the target account: from the account menu choose **Switch role**, and enter the account ID and the role name `OrganizationAccountAccessRole`.
5. Make the smallest fix.
6. Delete `breakglass-temp`, and write down what you did.

## Rolling back

Prefer rolling forward: run `git revert <commit>` on a new branch, open a pull request, read the preview, merge and approve. A revert does not bring deleted data back. A change that replaces a bucket keeps the old one (`UpdateReplacePolicy: Retain`); a deleted stack or bucket is gone for good.

## Removing a project

1. Empty each of its buckets: S3 console → the bucket → **Empty** (this removes old versions too).
2. Delete its stacks in dev and prod, in the console or with the command from "The budget brake fired", step 2. If one stops at `DELETE_FAILED`, a bucket was not empty yet: empty it and delete again.
3. In a pull request, delete `projects/<project>/` and `.github/workflows/deploy-<project>.yml`.

## Adding and removing people

Before adding anyone, close the accepted risks that say "before adding a collaborator". To add an engineer, create an Identity Center user with only the permission sets they need, and add them to GitHub, `CODEOWNERS` and the `prod` reviewers. To remove one, disable the Identity Center user and remove them from GitHub.

If you suspect GitHub is compromised, change the plan and deploy roles' trust policies to deny all, or delete the OIDC provider, in each workload account. Then rotate your GitHub credentials, and search CloudTrail for sessions named `plan-<run id>` or `deploy-<project>-<run id>`.

## A Dependabot alert names a package you never installed

`uv.lock` pins every package your tools depend on, so Dependabot can alert on any of them. They run only in CI and on your Mac, never in AWS: treat an alert as real but not urgent.

1. See which tool brings the package in: `uv tree --invert --package <name>`.
2. Try a normal upgrade: `uv lock --upgrade-package <name>`. If `uv.lock` changes, open a pull request.
3. If nothing changes, the tool pins that exact version. Wait for the tool's next release, or force a fixed version with `override-dependencies = ["<name>==<version>"]` under `[tool.uv]` in `pyproject.toml`, with a comment saying when to remove it.

## What you can rebuild

A lost workload account can be rebuilt from code. The data cannot. Decide how you would recover data before putting anything valuable in a bucket.

8.1What "hardened" means here

The first project, sample, is one stack with four resources: a data bucket, a bucket for its access logs, and a policy on each. Each control answers one risk, and the service role from section 5 already allows exactly these resources.

Control Resource Risk it answers
Default encryption with S3-managed keys (SSE-S3) Both buckets Unencrypted data at rest, with no key to pay for or manage
Block Public Access on, ACLs disabled Both buckets Accidental public exposure
Bucket policy that refuses plain HTTP Both policies Data read or written without encryption in transit
Bucket policy that refuses uploads asking for another encryption type DataBucketPolicy One object encrypted differently from the rest
Server access logging to the log bucket DataBucket, AccessLogBucketPolicy No record of who read or wrote what
UpdateReplacePolicy: Retain, with DeletionPolicy: Delete Both buckets A change that replaces a bucket destroying its data. Deleting the stack still removes both (decision D13)

SSE-S3 encryption is free. If you later want a key of your own, Appendix A shows how, at about USD 1 per key per month.

9. Your day-to-day workflow

Why this section After the build, almost everything you do is the same short loop. Following it every time is what keeps the setup safe: the previews are the review, and skipping them is the one way to lose the protection you built.

Example The sample project needs a second bucket. You add it to the template, open a pull request, read two previews that each show the new rows as Add, merge, watch dev succeed and approve prod. That is the whole job.

9.1The loop for every change

  1. Branch. git switch main && git pull, then git switch -c feature/<short-description>. One logical change per branch.
  2. Edit the project's files under projects/<project>/, following the rules in the table below.
  3. Check locally: uv run cfn-lint projects/<project>/stacks/*/template.yml, then cfn-guard validate --rules guard/ --data <template> for each template you changed.
  4. Commit, push and open a pull request. In the description, say which projects and environments change and what could go wrong.
  5. Read both previews in the check summaries. This is the review step. Never skip it for prod.
  6. Merge when every check is green.
  7. Watch dev deploy and check it there. Then reread the prod preview and approve.
  8. Verify prod with the read-only profile. If anything fails, use the runbooks in section 11.

How to read a preview. Look at the Action and Replacement columns; the script also prints a warning on any removal or replacement.

You see It means What to do
Add A new resource Check its name and settings
Modify, replacement False Changed in place Check which property changes
Modify, replacement True or Conditional The resource may be destroyed and created again Stop. Work out what happens to its data before merging
Remove The resource is deleted Stop. A removed bucket or table is deleted with its data (decision D13): confirm you no longer need it
no changes The stack already matches Nothing to review for that stack

9.2Rules every template follows

Rule Why
Name every resource <org>-<env>-<project>-..., using the OrgPrefix and Environment parameters The service role may only create names starting <org>-<env>-, and the project part keeps projects from colliding
Keep one template per stack, and put what differs between dev and prod in dev.json and prod.json Prod runs exactly the template you tested in dev
Set UpdateReplacePolicy: Retain and DeletionPolicy: Delete on anything that holds data A change that replaces it keeps the old copy, and deleting the stack removes everything (decision D13)

9.4Give a project its own IAM role

Workloads often need a role, for example a Lambda function that reads the data bucket. The service role creates it only if the role is named <org>-<env>-... and carries the permissions boundary, which stops the new role from ever changing identities, the organization or the account. A role created without the boundary is refused.

9.4.1Read

The two lines every role needs

Inside a template's Resources
  ReaderRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: !Sub '${OrgPrefix}-${Environment}-sample-reader'
      PermissionsBoundary: !Sub 'arn:aws:iam::${AWS::AccountId}:policy/${OrgPrefix}-workload-boundary-${Environment}'
      AssumeRolePolicyDocument:
        Version: '2012-10-17'
        Statement:
          - Effect: Allow
            Principal:
              Service: lambda.amazonaws.com
            Action: 'sts:AssumeRole'
      Policies:
        - PolicyName: read-data
          PolicyDocument:
            Version: '2012-10-17'
            Statement:
              - Effect: Allow
                Action: 's3:GetObject'

RoleName and PermissionsBoundary are the two lines that matter. The role's own policy still decides what it may do: here, only read objects from the data bucket.

9.5Let the pipeline create a new kind of resource

Today the service role can create S3 buckets and roles that carry the boundary, nothing else. Each new AWS service is a deliberate platform change, made in its own pull request and deployed by you. Never widen the role to * to clear an error.

9.6Run a project's tests in CI

Lint and policy scan checks templates, workflows and scripts, and holds no AWS credentials. A project whose own tests need more, such as a database or a model on Amazon Bedrock, gets a job of its own in pr-validate.yml. Three rules keep that job from weakening the pipeline:

  • Its own role, never the plan role. The plan role previews and nothing else, and the checks in section 10 rely on that. Tests that need AWS sign in with a role of their own: dev only, trusting the same pull-request subject as the plan role, and allowed only what the tests need.
  • It reports on every pull request. A required check blocks merging until it reports, and a workflow that a paths: filter stops from running never reports. So the job always runs: its first step asks changed-projects.sh whether the project changed, and if not, the job skips its other steps and still ends green.
  • A job in the shared workflow, for now. A project's job in pr-validate.yml is a shortcut, recorded as D14 in docs/decisions.md. When a second project needs its own job, move each project's steps into a script in its folder and run them all from one shared job.

9.6.2Editor

Add the project's job to pr-validate.yml

Add the job under jobs:, after the preview job, in a pull request of its own. This skeleton has the parts every project's job needs; fill in the project's test commands. If Dependabot has moved the pinned SHAs since, copy the uses: lines from the jobs already in the file.

Added under jobs in .github/workflows/pr-validate.yml
  <project>-tests:
    name: <project> tests
    needs: validate
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    permissions:
      id-token: write
      contents: read
    steps:
      - name: Check out the code (full history, to compare with main)
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false

      # Decided here, not with a paths filter, so the check reports on every pull request.
      - name: Did this pull request change <project>?
        id: changed
        env:
          BASE_REF: origin/${{ github.base_ref }}
        run: |
          projects="$(./scripts/changed-projects.sh "$BASE_REF")"
          if grep -qx <project> <<< "$projects"; then
            echo "run=true" >> "$GITHUB_OUTPUT"
          else
            echo "No <project> changes: tests skipped." | tee -a "$GITHUB_STEP_SUMMARY"
          fi

      - name: Run the tests that need no AWS
        if: steps.changed.outputs.run == 'true'
        working-directory: projects/<project>
        run: <its tests that need no AWS>

      - name: Assume the evals role
        if: steps.changed.outputs.run == 'true'
        uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
        with:
          role-to-assume: arn:aws:iam::${{ vars.DEV_ACCOUNT_ID }}:role/${{ vars.ORG_PREFIX }}-github-evals-dev
          role-session-name: <project>-tests-${{ github.run_id }}
          aws-region: ${{ vars.AWS_REGION }}
          allowed-account-ids: ${{ vars.DEV_ACCOUNT_ID }}

      - name: Run the tests that need AWS
        if: steps.changed.outputs.run == 'true'
        working-directory: projects/<project>
        run: <its tests that need AWS>
  • needs: validate waits for the lint job, and id-token: write is on this job only.
  • Every step after the first carries if: steps.changed.outputs.run == 'true'. A skipped run still ends green, so the check reports on every pull request.
  • Never add a paths: filter to pr-validate.yml: a workflow that does not run leaves its required checks waiting for ever.
  • Run what needs no AWS before the sign-in step, so as little as possible runs with credentials. If the job sets up uv, give it enable-cache: false: no shared cache in a job that later holds AWS credentials.
  • While the budget brake is attached, this job fails like the previews do, until you release it.

Check it from the repository folder, as in 7.5.3:

10. The security model

Why this section It is easy to feel secure without knowing why. This section lists the six things that could realistically go wrong with this setup, what stops each one, and what still gets through. Reread it every quarter, and before you add a second person.

Example A stranger forks your public repository and opens a pull request that edits a workflow to grab AWS credentials. The fork's run gets no secrets, the plan role trusts only pull requests from your own repository, and even if it signed in, the plan role cannot change anything.

10.1The six threats that matter

Each threat is stopped by more than one control. The last column is what still gets through; each of those is listed as an accepted risk below.

11.3The budget brake fired

You get an email saying the budget action ran. Dev and prod are now frozen: previews, deploys and your workloads' own AWS calls fail with explicit deny in a service control policy. You can still sign in through Identity Center and clean up.

  1. Find what costs money. In the management account, open Billing and Cost Management → Cost Explorer, group by Service, and look at the last 7 days.

  2. Stop it. Delete or scale down the resource. To delete a whole stack, use the console or an admin profile: CloudFormation does the work with the service role, which the brake leaves alone. Empty its buckets first.

    Terminal
    aws cloudformation delete-stack --stack-name <stack> --profile <org>-<env>-admin

  3. Release the brake from the management account. The first command prints the action ID and EXECUTION_SUCCESS; the second releases it:

    Terminal
    aws budgets describe-budget-actions-for-budget --account-id <mgmt-account-id> --budget-name <org>-monthly --query 'Actions[].[ActionId,Status]' --output text --region us-east-1 --profile <org>-mgmt-admin
aws budgets execute-budget-action --account-id <mgmt-account-id> --budget-name <org>-monthly --action-id <action-id> --execution-type REVERSE_BUDGET_ACTION --region us-east-1 --profile <org>-mgmt-admin

  4. A released brake stays off for the rest of the month. On the first day of the next month, run the first command again. It should print STANDBY; if it does not, re-arm the brake with --execution-type RESET_BUDGET_ACTION.

11.4Drift

Drift means something in AWS no longer matches its template, usually because someone changed it by hand.

Terminal
aws cloudformation detect-stack-drift --stack-name <stack> --query StackDriftDetectionId --output text --profile <org>-<env>-admin
aws cloudformation describe-stack-resource-drifts --stack-name <stack> --stack-resource-drift-status-filters MODIFIED DELETED --profile <org>-<env>-admin

Wait about a minute between the two commands. Resolve every difference: put the real change into the template, or put the resource back.

11.5Break-glass: when the normal route is unavailable

Escalate only as far as you must, and clean up afterwards.

Level 1: the pipeline is down or too slow.

  1. Sign in with aws sso login --sso-session <org>.
  2. Make the smallest change that stops the harm.
  3. Write down what, why and when.
  4. Put the same change into code the same day.
  5. Run drift detection, and review your session in CloudTrail.

Level 2: Identity Center is down, or you are locked out. A last resort. Read it now; do not rehearse it.

  1. Sign in at https://console.aws.amazon.com/ as the management root user, with its password and one MFA device from Bitwarden.
  2. In IAM, create a temporary user named breakglass-temp with the AdministratorAccess policy and a console password.
  3. Sign out, then sign in as breakglass-temp.
  4. Switch role into the target account: from the account menu choose Switch role, and enter the account ID and the role name OrganizationAccountAccessRole.
  5. Make the smallest fix.
  6. Delete breakglass-temp, and write down what you did.

11.6Rolling back

Prefer rolling forward: run git revert <commit> on a new branch, open a pull request, read the preview, merge and approve. A revert does not bring deleted data back. A change that replaces a bucket keeps the old one (UpdateReplacePolicy: Retain); a deleted stack or bucket is gone for good.

11.7Removing a project

  1. Empty each of its buckets: S3 console → the bucket → Empty (this removes old versions too).
  2. Delete its stacks in dev and prod, in the console or with the command from "The budget brake fired", step 2. If one stops at DELETE_FAILED, a bucket was not empty yet: empty it and delete again.
  3. In a pull request, delete projects/<project>/ and .github/workflows/deploy-<project>.yml.

11.8Adding and removing people

Before adding anyone, close the accepted risks that say "before adding a collaborator". To add an engineer, create an Identity Center user with only the permission sets they need, and add them to GitHub, CODEOWNERS and the prod reviewers. To remove one, disable the Identity Center user and remove them from GitHub.

If you suspect GitHub is compromised, change the plan and deploy roles' trust policies to deny all, or delete the OIDC provider, in each workload account. Then rotate your GitHub credentials, and search CloudTrail for sessions named plan-<run id> or deploy-<project>-<run id>.

11.9A Dependabot alert names a package you never installed

uv.lock pins every package your tools depend on, so Dependabot can alert on any of them. They run only in CI and on your Mac, never in AWS: treat an alert as real but not urgent.

  1. See which tool brings the package in: uv tree --invert --package <name>.
  2. Try a normal upgrade: uv lock --upgrade-package <name>. If uv.lock changes, open a pull request.
  3. If nothing changes, the tool pins that exact version. Wait for the tool's next release, or force a fixed version with override-dependencies = ["<name>==<version>"] under [tool.uv] in pyproject.toml, with a comment saying when to remove it.

11.10What you can rebuild

A lost workload account can be rebuilt from code. The data cannot. Decide how you would recover data before putting anything valuable in a bucket.

Appendix A. Optional: a customer-managed KMS key

The data bucket encrypts with S3-managed keys, which cost nothing. A customer-managed KMS key makes reading the data a separate, auditable permission, and lets you cut off all access by disabling the key. It costs about USD 1 per key per month, so about USD 2 for dev and prod together: 40% of your $5 budget, before request charges. Skip this unless you want that control, and try it in dev first.

It is two changes, in this order: a platform change, then a project change.

A.1Let the service role manage keys

A.1.1Editor

Platform: widen the service role

Find the permissions with aws cloudformation describe-type --type RESOURCE --type-name AWS::KMS::Key --query Schema --output text --profile <org>-dev-readonly | jq '.handlers | map_values(.permissions)', and the same for AWS::KMS::Alias. In bootstrap/workload/pipeline-identity.yml, add to the service role's stack-resources policy:

  • kms:CreateKey, which cannot be limited to one key, so it needs Resource: '*'.
  • The key-management actions, on keys in this account and Region.
  • The alias actions, on alias/<org>-<env>-* and on the keys.

Ship it in its own pull request, then deploy it by hand in both accounts:

Terminal
cd <repo-dir>
for env in dev prod; do
  aws cloudformation deploy --stack-name <org>-pipeline-identity --template-file bootstrap/workload/pipeline-identity.yml --parameter-overrides OrgPrefix=<org> Environment=$env "GitHubSubjectPrefix=<subject-prefix>" --capabilities CAPABILITY_NAMED_IAM --region <region> --profile <org>-$env-admin
done

A.2Switch the data bucket to the key

A.2.1Editor

Project: add the key and use it

  1. In projects/sample/stacks/00-bucket/template.yml, add a key and an alias under Resources:

    Added under Resources
      DataKey:
    Type: AWS::KMS::Key
    # Deleted with the stack (decision D13): AWS then waits 30 days before
    # it removes the key for good.
    DeletionPolicy: Delete
    UpdateReplacePolicy: Retain
    Properties:
      Description: !Sub '${OrgPrefix}-${Environment} data bucket key'
      EnableKeyRotation: true
      KeyPolicy:
        Version: '2012-10-17'
        Statement:
          - Sid: EnableAccountAdministration
            Effect: Allow
            Principal:
              AWS: !Sub 'arn:aws:iam::${AWS::AccountId}:root'
            Action: 'kms:*'
            Resource: '*'

  DataKeyAlias:
    Type: AWS::KMS::Alias
    Properties:
      AliasName: !Sub 'alias/${OrgPrefix}-${Environment}-sample'
      TargetKeyId: !Ref DataKey

  2. Switch only DataBucket to the key. Leave AccessLogBucket on AES256, because S3 delivers access logs only to a bucket with S3-managed keys:

    DataBucket's BucketEncryption
          BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: aws:kms
              KMSMasterKeyID: !GetAtt DataKey.Arn
            BucketKeyEnabled: true

  3. In DataBucketPolicy, change the value AES256 in the encryption rule to aws:kms.

  4. Ship it with a pull request. Each preview shows two Add rows, for the key and the alias, and Modify rows for the bucket and its policy, with replacement False.

After the deploy, the encryption test is reversed: an upload with no header is stored as aws:kms, and an upload that asks for AES256 is refused.
