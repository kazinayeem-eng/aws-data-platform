Agentic Pipeline Assurance: learn it by building it

A step-by-step guide for one learner, working 2–3 hours a week on a Mac. Every phase tells you what to do, why you are doing it, and how to know it worked — so you understand the system you are building, not just copy it. Nothing here builds anything for you. You type every command.

How to use this guide

This guide is the how. The Build Plan is the what and why — the architecture, the decisions, the cost model. Keep both open. When this guide says “see ADR-004”, it means the decision record in §8 of the plan; read it before you act on it.

The learning loop, every sitting: (1) read the phase's “idea” first, so you know what you are about to learn; (2) do one step at a time, in order; (3) check the “you should see” box before moving on — if it doesn't match, stop and fix it there, because every later step assumes the earlier one worked; (4) at the end of the phase, run the “check yourself” list. A phase is done when its checks pass, not when you feel done.

One sitting, one visible result. At 2–3 hours a week, a phase is 2–6 sittings. If a sitting ends with nothing working, the step is too big — split it. Getting stuck is part of the learning; the “watch out” box in each phase names the traps people actually hit.

Conventions. Commands you type start with $ and run in your Mac terminal (zsh), inside the repo unless stated otherwise. ap-southeast-2 is the region everywhere — if a console page shows another region, switch it before you click anything. Never paste AWS keys, passwords, or tokens into the repo, a chat, or a screenshot.

The one rule that matters most

Never let an agent — or a guide — do something you can't explain back in one sentence. If a step works but you don't know why, stop and re-read the “why” box. The portfolio is the understanding, not the repo.

Phase 0 · 1 week · $0

Foundations: your machine, your account, your repo

The idea

Before any agent code, you need three things to be true: your Mac can build and run Python reliably, your AWS account is safe to experiment in, and the two genuine unknowns are answered. The unknowns are: (1) does your paid account still hold any RDS free-tier hours, and (2) can you actually call Bedrock models in Sydney. Everything later assumes both answers are written down.

1Install uv, the Python tool

uv is one small program that replaces three things you may have met before: pip (installing packages), venv (making isolated environments), and pyenv (installing Python itself). One tool means one place for things to go wrong, and it is roughly 10–100× faster than pip — which matters when you reinstall often while learning.

Check first: run uv --version. If it prints a version number, uv is already installed — skip this step entirely. Only install it if the terminal says “command not found”.

$ curl -LsSf https://astral.sh/uv/install.sh | sh
$ uv --version    # expect something like: uv 0.5.x or newer
Why uv, not pip + venv

pip installs whatever is newest today, so “it worked on my machine” breaks on someone else's. uv writes a uv.lock file pinning every package to an exact version, and that file is committed to the repo — anyone cloning the repo gets the identical environment. For a portfolio, that reproducibility is the point.

You should see

uv --version prints a version number. If the terminal says “command not found”, close and reopen the terminal (the installer adds uv to your PATH) and try again.

2Install Python 3.12 and pin it

Python 3.12 is the version the whole project targets. Check first with uv python list: if 3.12 is already there, skip the install and just pin it. “Pin” means the repo records the version, so nobody accidentally runs it on 3.13 and finds a library behaves differently.

$ uv python install 3.12
$ uv python pin 3.12     # run inside stacks/agentic-pipeline-assurance/ later; writes .python-version
Why pin a version

Python libraries change behaviour between versions. Pinning removes an entire class of “works for me” bugs before they can happen, and it costs one command.

Your deployment pipeline already works in kazinayeem-eng/aws-data-platform — OIDC identity, a dev → prod deploy workflow, and PR validation with cfn-lint. The project is a new stack inside that repo, not a new repo. Check first: run git --version. If it prints a version, git is ready. If it says “command not found”, install the Xcode Command Line Tools first with xcode-select --install.

You don't need to understand every line yet — just notice that the workflow authenticates with id-token: write (that's OIDC: GitHub asks AWS for a short-lived credential instead of storing a permanent key) and that templates live under stacks/**/template.yaml.

So create the skeleton there, and run uv init from inside it. Note that uv init also creates a stray main.py you don't need — delete it. From here on, run the Python commands (uv run, pytest) from inside stacks/agentic-pipeline-assurance/ — that is the project root. The CloudFormation template lives there too (template.yaml); docs/adr/ lives at the repo root.

Why a skeleton first

Every later phase adds files into folders that already exist. If you create folders as you go, you end up reorganising mid-project and breaking imports. The skeleton is also the first thing a reviewer sees — a clean layout signals a clean mind.

4Start Postgres locally with Docker — check Docker first

Check first: run docker --version. If it prints a version, Docker is installed — skip straight to the compose file below. If it says “command not found”, install Docker Desktop for Mac first, open it, and wait for it to say “Running” before continuing.

Postgres runs on your Mac in Docker for Phases 1–7 (ADR-004). Create docker-compose.yml in the stack directory (the project root, where you are now) with a Postgres 16 image and the pgvector extension, then start it. pgvector is what lets Postgres store and search embeddings in Phase 3 — you install it now so the database never changes shape later.

$ cat > docker-compose.yml <<'EOF'
services:
  postgres:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_USER: apa
      POSTGRES_PASSWORD: apa-dev-only
      POSTGRES_DB: assurance
    ports: ["5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
volumes: {pgdata: {}}
EOF
$ docker compose up -d
$ psql "postgresql://apa:apa-dev-only@localhost:5432/assurance" -c "SELECT version();"
Why Docker, not installing Postgres on the Mac

Docker gives you a disposable database: if it breaks, you delete the container and start again in a minute, with no leftover software on your laptop. And the exact same image runs in CI, so “works locally” means something.

You should see

psql prints the Postgres version. If Docker says it isn't running, open Docker Desktop first and wait for it to say “Running”.

Then configure it to use your account. Prefer SSO if your account has it; otherwise a named profile. Your account ID and user/role ARN. Check the account ID matches the one in your AWS console — if it doesn't, you are signed into the wrong account.

6Put the budget alarms in before any resource exists

Go to the AWS console → Billing → Budgets → Create budget. Create two: one at $5 and one at $10, both alerting your email. Do this now, while the account is empty, because an alarm created after a runaway resource is an alarm that arrives too late. This is the cheapest insurance in the whole project.

Why alarms before resources

Every cost horror story starts with “I meant to turn it off”. A $5 alarm is the tripwire that tells you something is running that shouldn't be — usually a forgotten RDS instance, which is exactly the trap this project is built around.

7Spike A — do you have any RDS free-tier hours left?

In the console, go to Billing → Free Tier. Look for “Amazon RDS” and check the remaining hours. Write the answer in one line in docs/adr/adr-004.md (you'll copy the ADRs in step 9) — for example “0 hours remaining, verified 18 Nov 2026”. If hours remain, the plan changes: RDS could be used from Phase 1 at no cost. If not, the plan's local-Postgres decision is confirmed.

Why this is a “spike”

A spike is a small, time-boxed investigation that answers one question before you build on top of it. The whole cost model rests on this answer, so guessing would be worse than spending 10 minutes checking.

8Spike B — find the Nova Micro ID that works in Sydney, and make one real call

Bedrock now grants access to serverless foundation models by default — there is no per-model access request to file. (Anthropic models are the exception: they still need a one-time usage form, so file that for Claude Haiku if you plan to use it in Phase 7.) The real unknown is the model ID: Nova Micro in Sydney may need an apac. cross-region inference profile ID rather than the plain model ID amazon.nova-micro-v1:0. So test it. Try the plain ID first; if that fails, retry with the inference profile ID. Whichever one works, write it down in ADR-002 — every later phase uses that ID.

$ aws bedrock-runtime invoke-model \
    --model-id amazon.nova-micro-v1:0 \
    --region ap-southeast-2 \
    --cli-binary-format raw-in-base64-out \
    --body '{"messages":[{"role":"user","content":[{"text":"Say hello in one word."}]}],"inferenceConfig":{"maxTokens":10}}' \
    /tmp/bedrock-test.json
$ cat /tmp/bedrock-test.json

If the plain ID fails, retry with --model-id apac.amazon.nova-micro-v1:0 (the cross-region inference profile) and record the working ID in docs/adr/adr-002-bedrock-nova-micro.md. The --cli-binary-format raw-in-base64-out flag is needed in AWS CLI v2 because the --body is raw JSON.

Why one call now

If the model ID is wrong, you want to find out in Phase 0, when the fix is a different string — not in Phase 2, when you're debugging an agent and can't tell whether the model, the code, or the access is broken. One successful call removes that whole category of doubt.

You should see

The JSON file contains a short reply from Nova Micro. If you get an access error, re-check the region. If the plain model ID is rejected, try the apac. inference profile ID — that is the expected fix, not a failure.

Phase 1 · 2 weeks · < $1

The pipeline, no agents: make the load fail properly

The idea

Agents are useless without a system to look after. So first you build the system without any agent: a nightly data load (S3 → Lambda → Postgres) that works, plus a way to break it in exactly the way the walkthrough describes — a column renamed by the source system. If you can't make the failure happen on demand, you can't test whether an agent can fix it. This phase teaches you the four AWS building blocks everything else stands on.

You will learnS3LambdaStep FunctionsEventBridgeETL (extract, transform, load)

1Write the seeder: 1.2M synthetic customers

Write scripts/seed_incident.py. It generates fake customer rows (id, name, email, cust_status, signup date, orders) into your local Postgres customers table — about 1.2M rows over 3 years of history. Use Python's random and faker (add it with uv add --dev faker) rather than real data. Generate in batches of 10,000 with executemany or COPY, or it will take forever — and that's a real lesson: bulk loading is a different skill from inserting one row.

Why synthetic data, and why 1.2M rows

Real customer data must never enter a learning project. Synthetic data is safe and you control it — including the incident. And 1.2M rows is big enough that slow approaches hurt, which is how you learn to care about batching; 100 rows would teach you nothing about scale.

You should see

SELECT count(*) FROM customers; returns ~1,200,000, and SELECT min(signup_date), max(signup_date) FROM customers; spans about 3 years.

2Add the S3 bucket to the template

In stacks/agentic-pipeline-assurance/template.yaml, add an S3 bucket for the nightly CSV files, with a lifecycle rule that deletes objects after 7 days. S3 is where the “source system” drops its file every night. The 7-day rule is deliberate: raw files are transient, and storage you forget about is money you forget about.

Why S3, not a database, for the incoming file

S3 is the universal inbox of AWS: anything can write a file there, it's effectively unlimited, and it costs almost nothing at this scale. Pipelines start with a file landing somewhere — S3 is that somewhere.

3Write the ingest Lambda (S3 → Postgres)

Write src/pipeline/ingest.py: a handler that Step Functions invokes (see step 5) — it downloads the CSV from S3 and loads it into a staging table. There is no S3 event trigger on ingest; the load is driven by the Step Functions state machine on its schedule. Keep it small — one function, one job. It should log how many rows it read. Test it locally first with uv run python -m src.pipeline.ingest against a local CSV file, before it ever touches AWS. Local-first testing is a habit that will save you hours in every later phase.

Why Lambda, and why one job per function

Lambda runs your code when something happens and charges only while it runs — perfect for a job that happens once a night. One job per function means when ingest breaks, transform still works, and you can test each piece alone. A function that does everything is a function you can't debug.

4Write the transform Lambda (staging → live table)

Write src/pipeline/transform.py: it reads the staging table, applies the current column mapping, and writes to customers. The files are nightly deltas and live keeps the contract column cust_status, so the mapping (v1) is cust_status → cust_status. It must fail loudly — raise an exception with the column name in the message — if an expected column is missing. That failure message is what the Detector will read in Phase 2, so make it precise: “column cust_status not found in staging; found: customer_status”.

Why fail loudly

A transform that silently skips bad rows produces a table that looks fine and is wrong — the worst kind of bug. Failing loudly, with the exact column names, is what makes the system diagnosable. Good errors are a feature.

5Wire it together with Step Functions and EventBridge

Step Functions is the state machine: Ingest → Transform → Success, with a failure branch on any error. Write it as JSON in the CloudFormation template (the AWS::StepFunctions::StateMachine resource). Then add an EventBridge Scheduler rule for 02:00 daily, plus a manual trigger — you'll use the manual trigger constantly while learning, because waiting until 2am to test is not a workflow.

Why a state machine, not one big Lambda

A state machine makes the pipeline visible: you can open the console and see which step failed, with its input and output. A single Lambda hides all of that inside logs. Visibility is the difference between a system you can operate and a black box.

You should see

In the Step Functions console, a manual execution goes Ingest → Transform → Succeeded, and the customers row count goes up.

6Break it on purpose: the column rename

Add a flag to the seeder (--rename-column) that writes the nightly CSV with customer_status instead of cust_status — exactly the walkthrough's incident. Run the pipeline with the flag and watch it fail: the transform raises, Step Functions takes the failure branch, and the live table is untouched (stale, not wrong).

Why you must be able to break it on demand

Every agent you build later is tested against this failure. If the failure is hard to reproduce, testing is hard, and untested agents are just demos. “Break it on purpose” is the single most valuable testing skill in this project.

7Build the tiny dashboard

Write the dashboard publisher: a small function (src/pipeline/publish_dashboard.py) that reads the table and writes a one-page dashboard/index.html showing “fresh” or “stale”. A static S3 site cannot query Postgres, so the publisher does the reading and writes the numbers into the page — run it locally with uv run after each load for now; it deploys as a Lambda in Phase 8. Freshness is a load timestamp written by the transform on each run — not the newest signup_date. The dashboard is how a human sees the incident: fresh numbers mean healthy, stale numbers mean something broke overnight.

You should see

After a clean run the dashboard says fresh with the run's load timestamp; after a renamed-column run it says stale with the previous run's timestamp. Both states, on demand.

Check yourself — Phase 1 is done when all of these are true

  • A clean run loads and the dashboard shows fresh numbers.
  • A renamed-column run fails, Step Functions shows the failure branch, and the dashboard shows stale numbers.
  • The live table is never partially updated by a failed run (check the row count before and after).
  • Both runs are reproducible on demand with one command each.
Watch out

Lambda timeouts: the default is 3 seconds — loading a CSV needs more, so set the timeout to 60s in the template. Local Postgres vs the Lambda's connection: the Lambda in AWS can't reach your laptop's database; for Phase 1 the Lambdas run against the local Docker Postgres from your machine (via uv run) and the AWS deployment comes in Phase 8 — don't burn time wiring VPCs now. And always check the region before deploying the template.

Phase 2 · 2 weeks · < $1

The first agent: the Detector, tools, and the loop

The idea

Now something is allowed to look at the failure — but only through tools, and only with a brief. An agent is a loop: the model perceives (reads tool results), plans (decides the next tool call), acts (calls it), and observes (reads the result) until it can answer. The Detector's job is narrow on purpose: given a failed run, say what broke and cite the evidence. Narrow is good — a narrow agent is one you can test.

You will learnThe agent loopMCP / FastMCP tool serversTool allow-listsContext engineeringStrands Agents SDK

1Understand the loop before you code it

Before writing anything, read the Strands loop once. In the Strands source (inside your .venv, or on GitHub), find the main loop: it sends the conversation to the model, the model returns either text or a tool call, the tool runs, the result goes back into the conversation, repeat. Write one paragraph in the repo (docs/loop-note.md) explaining it in your own words. If you can't explain it, you don't understand it yet — and the rest of the phase will feel like magic.

Why read the framework code

Frameworks feel like magic until you read them. The Strands loop is about 100 lines. Reading it once turns “the agent decided” into “the model returned a tool call, the loop executed it, the result went back in” — and from then on, every strange behaviour has a place to look.

2Build the FastMCP tool server with two tools

Write src/tools/logs_server.py using FastMCP. Two tools only:

# src/tools/logs_server.py
from fastmcp import FastMCP
mcp = FastMCP("logs")

@mcp.tool
def read_job_logs(run_id: str) -> str:
    """Return the error lines for a pipeline run, not the whole log."""
    ...  # read the run's log, return only lines containing ERROR / the failure

@mcp.tool
def get_table_schema(table: str) -> dict:
    """Return the current column names of a table."""
    ...  # query information_schema, return {"columns": [...]}

if __name__ == "__main__":
    mcp.run()

Notice what each tool does not do: read_job_logs returns the error lines, not 40,000 raw lines. Tools are the agent's senses — a good tool returns exactly what the agent needs, already filtered. Test both tools by hand first: call them from a small script and read the output yourself.

Why MCP, and why two tools

MCP (Model Context Protocol) is the standard way to give a model tools: the server describes each tool (name, inputs, what it does), and any MCP-compatible agent can use it. Two tools is a deliberate constraint — with two tools you can prove the agent chooses correctly; with twenty, you can't tell choosing from guessing.

3Create the Detector with a 2-tool allow-list

Write src/agents/detector.py. In Strands, an agent is a model plus tools plus a system prompt:

from strands import Agent
from strands.models import BedrockModel
from strands.tools.mcp import MCPClient
from mcp.client.stdio import stdio_client, StdioServerParameters

model = BedrockModel(model_id="amazon.nova-micro-v1:0", region_name="ap-southeast-2")
# connect to your FastMCP server, then:
detector = Agent(model=model, tools=[read_job_logs, get_table_schema],
                 system_prompt="You are the Detector. Find what broke in the failed run. "
                               "Use only your tools. Cite the tool result for every claim.")
result = detector("Run 2026-11-18-0214 failed. What broke?")

The allow-list is the tools=[...] list. The Detector physically cannot call a tool that isn't in it — that is a design decision, not a request in the prompt. Use the model ID you recorded in ADR-002 in Phase 0 Spike B — if Spike B found an apac. inference profile ID works in Sydney, use that here instead of the plain ID. Run it against a real failed run.

You should see

The Detector calls read_job_logs, then get_table_schema, and reports: the transform failed because cust_status is missing, and the schema now has customer_status — citing both tool results.

4Build the context builder: the brief, not the log file

Write src/shared/context.py with a function build_brief(run_id) that returns a short brief with exactly 6 items — schema diff, runbook, owner, target, rules, deadline — and nothing else. The Detector receives the brief — never the raw logs. Then write the test that proves it:

# tests/test_context.py
# A known raw log line from the failed run — it must never appear in the brief.
RAW_LOG_LINE = "2026-11-18T02:14:03Z INFO ingest-worker-7 batch 412/40000 rows=10000"

def test_brief_is_small():
    brief = build_brief("2026-11-18-0214")
    assert len(brief) < 2_000          # characters, not tokens
    assert "cust_status" in brief
    assert RAW_LOG_LINE not in brief     # the raw log line must not leak in
Why the brief is the whole lesson of Phase 2

Models have limited attention and every token costs money. Dumping 40,000 log lines into the prompt is slow, expensive, and makes the model worse — it drowns the signal in noise. Context engineering is the discipline of giving the model exactly the information it needs, and this test is how you prove you did it. When agents misbehave later, the first question is always: “what was in the prompt?”

You should see

uv run pytest tests/test_context.py passes. Now break the brief on purpose (include the raw logs) and watch the test fail — that's the test earning its keep.

Check yourself — Phase 2 is done when all of these are true

  • Given a failed run, the Detector reports the missing column and cites the get_table_schema result.
  • Adding a third tool requires no change to the Detector's code (only the tools list).
  • The brief-size test passes, and fails when you deliberately break the brief.
  • You can explain the agent loop in one paragraph, in your own words (docs/loop-note.md exists).
Watch out

If the Detector “knows” the answer without calling tools, it is guessing from its training data — check that your system prompt and brief don't contain the answer. If a tool call fails, read the error from the MCP server first; most failures are a wrong path or a missing environment variable. Bedrock throttling shows up as a rate-limit error — wait a minute and retry; at learning volumes this is rare.

Phase 3 · 2 weeks · < $1

The Diagnoser: RAG, memory, and grounding

The idea

The Detector says what broke. The Diagnoser says why and what to do about it — and it must do that from evidence, not from vibes. Three ideas carry this phase: RAG (look up the runbook before explaining), memory (remember what happened last time), and grounding (every claim carries a source, or it is labelled unknown). These three are what separate an agent from a chatbot with tools.

You will learnEmbeddings & pgvectorRAG (retrieval-augmented generation)Short- vs long-term memoryGrounding & citationsDynamoDB basics

1Write the runbook and the data contract

Write two short Markdown files in docs/: runbook-4.2-column-renames.md (“Handling column renames”: check the schema diff, check the source change note, update the mapping, test on a copy first) and customers-contract.md (the customers table's columns and their meaning). Keep each under a page. These are the documents the Diagnoser will retrieve — and writing them forces you to decide what the correct procedure actually is, which is half the learning.

Why write docs for a machine to read

RAG only works if there is something worth retrieving. A runbook written for the agent is also a runbook for the human — and in a portfolio, it shows you can turn operational knowledge into something a system can use.

2Chunk, embed, and store them in pgvector

Write src/tools/index_docs.py: split each document into chunks of ~500 characters (split on headings and paragraph breaks, never mid-sentence), embed each chunk with Bedrock Titan (amazon.titan-embed-text-v2:0), and store the chunk text plus its embedding vector in a Postgres documents table with a vector column. Run it once and inspect the table — you should see rows with chunk text and a long list of numbers (the vector).

What an embedding actually is

An embedding turns text into a list of ~1,024 numbers that captures meaning: texts that mean similar things get similar numbers. That lets the database answer “find the chunk most similar to this question” with arithmetic (nearest neighbour) instead of keyword matching. Chunking matters because one whole document is too coarse — you want the one paragraph that answers the question, not the whole manual.

You should see

SELECT count(*) FROM documents; returns the number of chunks, and a similarity query for “column rename” returns the runbook chunk at the top.

3Add the search_runbook tool and the Diagnoser

Add search_runbook(query) to your MCP tool server: it embeds the query, finds the nearest chunks in pgvector, and returns their text. Then write src/agents/diagnoser.py with tools [search_runbook, get_table_schema, read_job_logs] and a system prompt that says: retrieve before you explain. Run it against the seeded incident.

You should see

The Diagnoser calls search_runbook first, then explains the failure by citing the runbook section and the schema diff — not by inventing a cause.

4Give it memory: DynamoDB, short-term and long-term

Create one DynamoDB table, apa-memory, with a partition key and a sort key (plan §7): short-term notes use PK=incident#2026-11-18, SK=note#…; long-term lessons use PK=lesson#sept-rename, SK=meta. Short-term: the Diagnoser writes notes about the current run. Long-term: write one lesson by hand — the September orders-table rename, fix: update the mapping. Approvals are never stored here — they live in apa-approvals (Phase 4). Then give the Diagnoser a recall_lessons tool that reads lessons before diagnosing.

Why two kinds of memory

Short-term memory is the run's scratchpad — it dies with the run. Long-term memory is what makes the system get better over time: the September lesson changes what the Diagnoser suggests today. If you can't tell which kind a piece of information is, you can't design memory at all.

You should see

Run the Diagnoser twice: once with the September lesson present, once with it deleted (temporarily). The suggested fix changes — that difference proves memory is load-bearing, not decorative.

5Enforce grounding in code

In the Diagnoser, add a rule — in code, not just in the prompt: every claim in the diagnosis must carry a source reference (a tool result, a runbook chunk, or a lesson). After the model answers, a small function checks the claims; any claim without a source is rewritten as “unknown”. Test it by asking about something with no evidence and confirming the answer says “unknown” instead of inventing one.

Why grounding must be code, not a prompt

A prompt says “please cite sources”. A model under pressure will still invent a confident answer. Code that checks the output and rewrites unsourced claims cannot be talked out of it. This is the pattern of the whole project: the important rules live in code, the prompt is only a suggestion.

Check yourself — Phase 3 is done when all of these are true

  • A 10-question retrieval test scores ≥ 8/10 (write 10 questions whose answers are in the runbook, and check the right chunk comes back).
  • The diagnosis for the seeded incident cites the log line, the schema diff, and the change note.
  • Deleting the September lesson changes the Diagnoser's suggested fix.
  • A question with no evidence gets “unknown”, not an invented answer.
Watch out

Chunks too big → retrieval returns whole documents and the model drowns; chunks too small → the answer is split across chunks. ~500 characters is a good starting point — tune it if the retrieval test scores low. DynamoDB on-demand has no servers to manage, but every item needs its keys right: if a read returns nothing, check the partition key value first.

Phase 4 · 4 weeks · < $1 · The phase that earns the portfolio

The Fixer: safety — sandbox, guardrails, policy, identity, approval

The idea

This is the longest phase because it is the most important one. The Fixer can repair the table — and, far more importantly, it cannot destroy it. Five safety ideas stack here, and each one is enforced in a different place, so that no single failure removes the protection: the sandbox (test before touching the real thing), the guardrail (block dangerous calls before they land), the policy (the swap needs an approval record), identity (the Fixer literally lacks permission to write production), and the human (a person approves the swap). If you only remember one phase in an interview, remember this one.

You will learnSandboxingGuardrail hooksPolicy enforcementPostgres roles & identityHuman-in-the-loopNegative testing

1Build the sandbox: write_test_copy

Add a tool write_test_copy that clones live into a customers_test table first, then loads tonight's files into it with the new mapping (v2: customer_status → cust_status), and reports the row count and error count. Cloning from live first is what makes a swap safe — the test copy starts as a true copy of live. The Fixer always works here first. Nothing in this tool touches the live table — read its code twice and confirm that by inspection before you run it.

Why a sandbox, not just “be careful”

“Be careful” is not a control. A separate table that you can drop and rebuild is a control: the blast radius of any mistake is a table nobody depends on. Every serious data system works this way — test copy first, live table only after proof.

You should see

After running it, customers_test is a clone of live with the new mapping applied and 0 load errors, while customers is unchanged.

2Add the three guardrail layers: hook, tool server, Postgres role

There are three independent layers, and each one must refuse on its own. (1) Guardrail hook: Strands lets you attach a hook that runs before a tool call. Add one that inspects every tool call the Fixer attempts: if the call would overwrite the live customers table in one step, the hook blocks it, logs the attempt, and returns an error to the model saying “use the test copy first”. (2) Tool-server authorisation: the MCP tool server knows which agent is calling and refuses a live-table write from the Fixer — the check lives in the server, not in the agent's prompt. (3) Postgres role: the Fixer's database role cannot write production at all (step 3), so even a call that got past the first two layers fails at the database. Then write the negative test for each layer on its own: disable the hook and confirm the tool server still refuses; bypass the tool server and confirm Postgres still refuses. In every case, assert the live table is byte-identical afterwards (same row count and a hash of the contents).

Why three layers, not a prompt

A prompt says “don't overwrite the live table”. A hook prevents it — the call never reaches the database. And one lock is not enough: if the hook had a bug, the tool server still refuses; if the tool server had a bug, Postgres still refuses. Three independent refusals is defence in depth. When you test it, you are testing the locks, and the test must try to break in — one layer at a time.

You should see

Each blocked attempt is logged, the model re-plans and uses the test copy instead, and the live table's row count and hash are unchanged — for each of the three layers, tested on its own.

3Give each agent its own Postgres role — and teach the tool server who is calling

Create separate Postgres roles, one per agent: the Fixer role can read production and write staging, and cannot write production. The Detector and Diagnoser get read-only roles. The MCP tool server authenticates which agent is calling and connects to Postgres as that agent's role, so the database itself enforces the boundary. Then test it: connect as the Fixer role and try to write to the live table — Postgres must refuse. IAM roles do not control Postgres writes and mean nothing on local Docker — the Postgres role is the layer that actually says no at the database. (IAM still governs the AWS side: which Lambda can call which AWS service.)

Why identity is a safety layer, not admin

Least privilege means every component has exactly the permissions it needs and no more. If the Fixer is ever compromised or confused, the damage it can do is bounded by its Postgres role. The database role is the one safety layer that works even when all your code is wrong — because it lives in the database, not in your code.

4Put the policy in the tool server, not the prompt

Add the swap_tables tool, and inside it — in the tool's own code — check the apa-approvals table for a matching approval record before doing anything. A record matches only if it names this incident ID, the hash of this test copy, has not expired, and has not been used before. If any of those four fails, no swap, full stop. The model cannot talk the tool out of this because the model never sees the check; it only sees “approval required”. The approval record lives in apa-approvals, never in apa-memory — an agent that can write memory cannot approve itself.

Why the check lives in the tool

Prompts are suggestions to a model that is very good at finding reasons to proceed. Code in the tool server is a gate. The rule for this project: if a rule matters, it lives in code or in the database role — the prompt is only ever a second opinion.

5Build the approve endpoint and the apa-approvals table

An SNS email cannot host a working Approve link — and email scanners auto-click links, so a bare link could approve by itself. So build a small approve endpoint: a Lambda behind a Function URL that serves a confirmation page. Create the apa-approvals DynamoDB table (incident ID, test-copy hash, expiry, used flag). Only this endpoint can write to apa-approvals — no agent, no tool, and no other Lambda has write access to it. The endpoint checks the signed single-use token from the confirm page and, if it is valid, writes the approval record.

Why a confirm page and a token

A link in an email is clicked by scanners, previewers, and curious humans — none of whom should be able to approve a live change. The confirm page means approving needs a deliberate click, and the signed single-use token means the click can only approve this incident, this test copy, once, before it expires. The endpoint is the one door, and the token is the key.

You should see

Opening the email link shows a confirmation page (not an instant approval). Clicking confirm writes one record to apa-approvals; clicking the same link again is refused as already used.

6Add the human: SNS email, confirm page, approval, swap

When the test copy loads cleanly, the system sends you an SNS email: what broke, what was tested (test-copy row count and errors), and exactly what will change if you approve. The email links to the confirm page on the approve endpoint — it does not approve by itself. You click through, confirm, and the endpoint writes the approval record to apa-approvals; then the Fixer runs swap_tables, which checks the record first. Step Functions holds the wait with waitForTaskToken (30-minute timeout) — the wait lives in Step Functions, not in an agent Lambda, so the 15-minute Lambda cap cannot be hit by an 18-minute human. Rejecting — or doing nothing until the timeout — leaves the live table alone and the incident open. Test all three paths: approve, reject, and timeout.

Why a human, and why email

Some decisions carry consequences a model should not take alone — swapping the table a whole company reads from is one of them. The approval step is real: it blocks the swap. Email is the simplest channel that works, and the timeout rule matters most: doing nothing must be safe, not a silent approval.

You should see

Approve → confirm page → approval record → swap happens, dashboard goes fresh. Reject → live table untouched, incident stays open. Timeout (30 minutes) → same as reject, and the system says so in the log.

Check yourself — Phase 4 is done when all of these are true

  • The full path runs end to end: blocked overwrite → test copy loads with 0 errors → approval email → confirm page → approval → swap → dashboard fresh.
  • No approval means no swap (tested).
  • A blocked overwrite leaves the live table byte-identical (tested) — for each of the three layers on its own.
  • A rejected approval leaves the live table alone (tested).
  • A timeout leaves the live table alone and the incident open (tested).
  • The Fixer Postgres role cannot write production even when asked directly (tested).
  • The approval record is in apa-approvals, written only by the approve endpoint — never in apa-memory.
Watch out

The negative tests are the phase — if you only test the happy path, you have tested nothing about safety. Also: SNS email delivery can be slow the first time (check spam, and confirm the subscription). And keep the approval record's key exact: a swap that looks up the wrong key will fail closed (safe, but confusing) — read the key twice. Never put the approval record in apa-memory: if an agent can write memory, it can approve itself.

Phase 5 · 2 weeks · < $1

The Verifier and the eval set: proof instead of “it worked”

The idea

Until now, “it works” has meant “I watched it work once”. That doesn't survive change. Phase 5 makes proof automatic: the Verifier checks the fixed table against four concrete checks, and a 20-case eval set scores the whole system on every change. From here on, a change that breaks the evals is a change that doesn't ship — and you can say, with numbers, whether a change helped or hurt.

You will learnVerification checksEvals (agent evaluation)Regression testingCI with GitHub Actions

1Write run_checks: the 4 checks from the walkthrough

Add a run_checks tool that runs four checks against a table and returns pass/fail for each: (1) row count = live-before + file rows, (2) column names match the contract and no null keys, (3) status values are in the contract set, (4) a 100-row sample matches the source. Each check is a small SQL query plus an assertion. The Verifier agent calls this tool — through MCP like every other agent; it has no direct Postgres access — and reports the results.

Why four specific checks, not “looks good”

“Looks good” is an opinion. Row count, column names and null keys, status values, sample match — those are facts a computer can verify, and each one catches a different failure mode (a partial load, a wrong mapping, an invalid status, corrupt data). Writing the checks is deciding what “fixed” means.

You should see

On a fixed table: 4/4 pass. On the broken table: at least the column-name check fails.

2Wire the Verifier in twice: before approval, and after the swap

The Verifier does not check once — it checks twice. Before approval: after the test copy loads, the Verifier runs the 4 checks on customers_test, and the approval request carries that result. A failing check blocks the approval request — there is nothing for the human to approve yet. After the swap: the Verifier re-runs the 4 checks on live customers, and a failure rolls back to customers_prev (the old live table, kept for exactly this). Update the Phase 4 flow so the approval email now includes the pre-approval 4-check result. Test both: a bad test copy never reaches the human, and a bad live table is rolled back.

Why twice, not once

Checking only after the swap means live is already wrong when a check fails — the damage is done and you're cleaning up. Checking the test copy first means the human only ever approves something already proven good, and the live check is the final safety net with a rollback behind it.

You should see

4/4 pass on the test copy before the approval email goes out; 4/4 pass on live after the swap. Break the test copy on purpose and confirm no approval email is sent; break live on purpose and confirm it rolls back to customers_prev.

3Build the 20-case eval set

In evals/, create 20 cases: 10 retrieval (questions about the runbook — did the right chunk come back?), 5 diagnosis (given a failure, is the cause right?), and 5 end-to-end replays (run the seeded incident through the system and score the outcome). Write a scoring script (evals/score.py) that runs all 20 and prints a score like “17/20”. The pass mark is ≥ 17/20 (85%) and the 4 checks 4/4 — a change that drops below it does not merge. Commit the score file with every change that produces it, so the score history is visible in git.

Why evals are different from unit tests

Unit tests check code: “does this function return the right value?” Evals check behaviour: “did the agent do the right thing?” A model can change its answer without any code changing, so you need a test that judges the answer. That is the eval set — and it is the gate between phases from now on.

4Break it on purpose and confirm the evals catch it

Deliberately break the column mapping, run the evals, and confirm the score drops. Then fix it and confirm the score recovers. This is the most important test in the phase: an eval set that never fails is a eval set that tests nothing. Write down the before/after scores.

You should see

Broken mapping → evals red (score drops below 17/20). Fixed mapping → evals green again (≥ 17/20). If the score doesn't move, your evals are too easy — make a case harder.

5Run the evals in CI on every push

Extend .github/workflows/pr-validate.yml with a job that installs dependencies with uv, runs pytest and the eval scoring script. It runs on every pull request — free for public repos. From now on, a PR that breaks the evals is visible before it merges, not after.

Why CI, not “I'll remember to run it”

You won't remember. Nobody does. CI is the version of you that never forgets, never gets tired, and runs the tests the same way every time. Putting evals in CI is what turns them from a nice idea into a gate.

Check yourself — Phase 5 is done when all of these are true

  • The 4 checks pass 4/4 on a fixed table — test copy and live.
  • The Verifier checks the test copy before approval is requested, and re-checks live after the swap, with rollback to customers_prev on failure.
  • The 20-case eval suite runs in CI and scores ≥ 17/20 (85%) — the pass mark.
  • The deliberate regression turns it red, and the fix turns it green again.
  • A reviewer can run the eval set from your README instructions alone.
Watch out

Evals that call Bedrock cost a little money and take time — keep the set at 20 cases, not 200. If CI is slow, check whether it's re-installing everything each run (uv caches help). And don't tune the evals to pass — if a case keeps failing, the system is wrong, not the test; fix the system or write down why the case is wrong and change the case openly.

Phase 6 · 2 weeks · < $1

The Orchestrator: four specialists become a team

The idea

So far you have four agents that work alone. Now one agent — the Orchestrator — takes the goal (“fix last night's failed load”), splits it into the four tasks, assigns them, and decides when a human is needed. The shape is hub-and-spoke: every handoff passes through the Orchestrator, which validates it before the next agent acts — agents never hand work directly to each other. The key skill of this phase is the handoff: the package of work one agent passes to the next, via the hub. A good handoff has a fixed shape and is validated on receipt — because in multi-agent systems, most failures are not bad reasoning, they are lost information between agents.

You will learnOrchestrationMulti-agent systemsA2A protocolHandoff schemas & validation

1Define the handoff schema first, in code

Before any agent talks to another, write the handoff shape in src/shared/handoff.py using Pydantic — the plan's five fields: done, next, owner, evidence (list of sourced claims), do_not_touch. Every field is required. do_not_touch is a safety field — it names what the next agent must not change (e.g. the live table) — never drop it. This is the contract — and writing it first is the lesson: in multi-agent systems, the interface is the design.

# src/shared/handoff.py
from pydantic import BaseModel, Field

class Evidence(BaseModel):
    claim: str
    source: str            # which tool result / runbook chunk / lesson

class Handoff(BaseModel):
    done: str
    next: str
    owner: str
    evidence: list[Evidence] = Field(min_length=1)   # at least one sourced claim
    do_not_touch: list[str] = Field(min_length=1)     # safety: what must not change
Why a schema, not free text

When agents pass free text, information quietly disappears — a claim loses its source, a task loses its context, and nobody notices until the fix is wrong. A schema makes the loss visible: if a required field is missing, validation fails loudly instead of silently.

2Write the handoff validator and break it on purpose

Write validate_handoff(data) — it parses the dict into the Handoff model and raises a clear error on failure. Then write the test: hand it a handoff with no evidence, and another with no do_not_touch, and confirm both are rejected and the run stops cleanly with an error, not a guess. This is the multi-agent version of Phase 4's guardrail: the system must refuse to proceed on incomplete information.

You should see

A valid handoff passes; a handoff missing evidence or do_not_touch raises a validation error naming the missing field.

3Build the Orchestrator

Write src/agents/orchestrator.py. Its system prompt says: you are the Orchestrator; your job is to split the goal into tasks, assign them in order (Detect → Diagnose → Fix → Verify), and decide when a human is needed. It does not do the work itself — it delegates. This is hub-and-spoke: every handoff passes through the Orchestrator, which validates it before briefing the next agent. Agents never hand work directly to each other — if the Diagnoser needs to tell the Fixer something, it goes through the Orchestrator. Give it the four agents as tools (each agent exposed as a callable), and the handoff validator between each step: the Orchestrator receives each handoff, validates it, and only then passes it on.

Why the Orchestrator doesn't do the work

One agent that does everything is one agent you can't test, can't replace, and can't reason about. Specialists are narrow and testable; the Orchestrator is the only part that knows the whole goal. That separation is the entire point of a multi-agent system — and it's what makes Phase 7's agent-swap test possible.

4Send tasks over A2A — same shape, in-process first

A2A (Agent-to-Agent) is the protocol for agents talking to each other: a task request, a task accepted, a task result. In this phase the agents run in the same process, but the messages use the A2A shapes — so when you move them to separate services later, the logic doesn't change, only the transport. Write the three message types as small dicts in src/shared/a2a.py and use them for every delegation.

Why use the protocol shape before you need it

Protocols are how parts stay swappable. If the Orchestrator calls agents directly with ad-hoc arguments, the agents are welded to it. If it sends A2A-shaped messages, any agent that speaks A2A can take the job — which is exactly what you'll prove in Phase 7.

5Run the seeded incident end to end, with no human except approval

Trigger the renamed-column incident, then run the Orchestrator with the goal “fix last night's failed load”. Watch the hub-and-spoke flow: the Orchestrator briefs the Detector, validates the handoff, briefs the Diagnoser, validates, briefs the Fixer (test copy, approval email, you approve, swap), validates, then briefs the Verifier. The only human step is the approval — everything else is the team, coordinated through the hub.

You should see

The incident goes from alert to verified fix, the dashboard goes fresh, and the trace shows four handoffs, each validated. Then remove one agent (e.g. disable the Verifier) and confirm its phase's test fails — proving each agent is load-bearing.

Check yourself — Phase 6 is done when all of these are true

  • The seeded incident runs from alert to verified fix with the Orchestrator delegating and the four agents handing off.
  • A malformed handoff is rejected by validation, and the run stops cleanly.
  • Removing any one agent makes its phase's test fail.
  • You can draw the message flow (Orchestrator → 4 agents → approval → verify) from memory.
Watch out

The classic multi-agent bug is the Orchestrator doing the work itself instead of delegating — if your Orchestrator's prompt contains the answer, it will skip the team. Keep its tools to delegation only. And if handoffs keep failing validation, the schema is probably too strict — loosen one field at a time, deliberately, and write down why.

Phase 7 · 3 weeks · $1–2

Observability, protocols, and the model comparison

The idea

A system you can't observe is a system you can't trust — or debug, or show anyone. This phase makes the system explain itself after the fact (traces), proves its parts are swappable (replace the Fixer and nothing else changes), and turns the model choice from a preference into a measurement (run the evals on two models and publish the numbers).

You will learnOpenTelemetry & X-Ray tracingCloudWatch dashboardsProtocol-based swappingMeasuring model choice

1Turn on tracing: one trace per incident

Enable OpenTelemetry in the Strands runtime and send traces to X-Ray. Each span should record: who acted (which agent), which tool was called, what came back, and how long it took. Then run the seeded incident and open the trace in the X-Ray console — you should be able to reconstruct the whole incident from it: Detector → Diagnoser → Fixer → approval → Verifier, with timings.

Why traces, not more logs

Logs are a pile of lines; a trace is a story with a shape. When something goes wrong at 2am, you don't want to grep — you want to open one trace and see the sequence. Tracing is also how you find the slow step: the span timings show you exactly where the minutes went.

You should see

One trace per incident in X-Ray, with a span per agent and per tool call, in order.

2Build the CloudWatch dashboard

In the CloudFormation template, add a CloudWatch dashboard with four graphs: runs per day, failures, approvals (granted / rejected / timed out), and eval scores over time. This is the operations view — the thing you'd look at every morning if this were a real system.

Why a dashboard, not just alarms

Alarms tell you something is wrong right now. A dashboard tells you whether things are getting better or worse over weeks — and in a portfolio, it shows you think about operating a system, not just building one.

3Swap the Fixer and change nothing else

Build a second Fixer — differently (different prompt, or a different model, or plain code instead of an agent) — behind the same MCP/A2A contracts. Swap it in, run the evals, and confirm they still pass with no other changes. This is the protocol test: it proves the contracts from Phases 2 and 6 are real, because a different implementation fits behind them.

Why swapping proves the design

Anyone can claim their agents are modular. Swapping one and watching the evals stay green is the proof. If the swap breaks things, the contracts were leaking — find where, and fix the contract, not the swap.

4Run the evals on Nova Micro and on Claude Haiku

Run the 20-case eval set twice: once with the default model (Nova Micro) and once with Haiku. Record three numbers for each: score, cost per run, and time per run. Publish the table in the README. Then decide — with the numbers in front of you — whether the default model (ADR-002) stays or changes. If it changes, write a new ADR saying so and why; that's what ADRs are for.

Why measure instead of prefer

“I like Haiku” is a preference. “Haiku scores 18/20 at $0.04/run vs Nova's 17/20 at $0.01/run” is a decision. Model choice is one of the most common engineering decisions you'll ever make, and this is how it's made properly — with numbers, in public, in the repo.

Check yourself — Phase 7 is done when all of these are true

  • A reviewer can open one trace and reconstruct the whole incident.
  • The swapped Fixer passes the evals with no other changes.
  • The model comparison table exists in the README with real numbers.
  • ADR-002 is either confirmed or changed by a new ADR, with the numbers cited.
Watch out

Tracing adds overhead and log volume — keep the 7-day retention so it can't surprise the bill. The model comparison is only honest if both runs use the same eval set and the same code — run them back to back, and don't tune prompts between runs.

Phase 8 · 2 weeks · ~$1–2 + one RDS day (~$0.50)

Ship it: the RDS demo, the portfolio, and switching off

The idea

The last phase is about the stranger: someone who has never met you opens your repo and decides, in ten minutes, whether you know what you're doing. Why the README is a deliverable, not an afterthought

In a portfolio, the README is the first thing a hiring manager reads and often the only thing. A repo with a great README and good code beats a repo with great code and no README, because the second one never gets read.

Appendix A

When you're stuck

Read the error, all of it. Most errors name the exact problem in the last two lines. Copy the error message into your notes before you start fixing — it stops you fixing the wrong thing.

Bisect. If something worked and now doesn't, find the last thing that changed and undo it. If a step fails, run the step before it again to confirm it still passes — that tells you whether the problem is here or upstream.

Check the region and the account first. Run aws sts get-caller-identity and look at the console region. Half of all AWS confusion is one of these two.

Ask the plan. Re-read the relevant ADR — it usually names the fallback. Then re-read the plan section for that phase and compare what you built against what it describes, with the exact error message in front of you. Bring the error, not a summary of it.

Take the win. If a sitting ends with one small thing working that didn't work before, that's a good sitting. Write down what changed — your future self will thank you.
