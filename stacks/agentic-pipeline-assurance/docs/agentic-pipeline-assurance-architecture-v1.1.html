The replay • The incident in 12 beats

02:00 to 08:00, in order

    The team

    Four specialists, one coordinator — hub-and-spoke

    Same Strands runtime, different system prompt and tool allow-list — and the allow-list is enforced by the tool server per agent identity, not just by the runtime. Every handoff passes through the Orchestrator.

    Data • Four stores, one job each

    Why this shape keeps you under $10/month

    Raw files

    S3 — …-raw

    Nightly extracts as they arrived — each file is a delta (new and changed rows), kept 7 days then lifecycle-expired. The renamed column is visible in the file itself, which is what makes the incident reproducible.

    s3://…/raw/dt=2026-11-18/customers.csv

    Analytics + RAG

    PostgreSQL + pgvector

    customers (live), customers_test (sandbox), customers_prev (kept after a swap, for rollback) and documents (runbook + contract chunks, vector(1024)) in one database.

    How RAG flows: Diagnoser asks → MCP search_runbook embeds the question → pgvector returns the nearest chunks → Diagnoser answers citing them. No chunk, no claim.

    Memory

    DynamoDB — apa-memory

    Short-term: this run's findings. Long-term: past incidents and fixes — e.g. September's rename, where the fix was update the mapping, don't rebuild. Agents read and write it. It holds no approvals.

    Approvals

    DynamoDB — apa-approvals

    A separate table in a separate trust boundary. Only the approve endpoint can write to it; agent roles and the memory client cannot. swap_tables() reads it and refuses unless a record matches this incident and this test copy, is unexpired, and is unused.

    🛡️

    Guardrails are code, not a prompt

    The Fixer's first idea — rebuild live from S3 — would trade 3 years for 7 days. Three layers refuse it independently: a client-side hook, the tool server (which knows which agent is calling), and the Postgres role the Fixer connects with. In the build, Phase 4 forces this attempt rather than waiting for the model to try it.

    🧪

    Sandbox, then check, then ask

    The fix is built in customers_test — a clone of live plus tonight's file. The same 4 checks the Verifier will run on live run on the test copy first, and the result goes in the approval email. Only a test copy that passes can request approval.

    ✋

    Approval is enforced by the tool — and reversible

    swap_tables() checks apa-approvals itself, in a store no agent can write. If nobody approves, the wait times out and live is untouched. The swap is one atomic rename that keeps customers_prev, so a failed post-swap check rolls back.

    What changed • v1.1 vs plan v1.0

    Corrections this page makes — the plan and guide need the same edits

    • Hub-and-spoke. Every handoff passes through the Orchestrator, which validates it. The agents no longer pass work to each other directly.
    • Failure path. Step Functions catches the Lambda failure and invokes the Orchestrator (the arrow used to start at the Lambda).
    • Approvals live in their own table (apa-approvals), writable only by the approve endpoint. Before, they sat in agent memory, so an agent with write access could approve itself.
    • New component: approve endpoint (Lambda Function URL). The email link opens a confirmation page and approving needs a deliberate click with a signed, single-use token, so link-prefetching email scanners can't approve.
    • Approval is bound to the incident, the test copy's hash and an expiry, and is single-use.
    • Step Functions holds the wait (waitForTaskToken). No agent Lambda sits waiting, so the 15-minute Lambda limit isn't hit by an 18-minute human.
    • Verifier runs twice. On the test copy before approval, and on live after the swap. A failed post-swap check rolls back to customers_prev.
    • Write protection is hook + tool-server authorisation per agent + Postgres roles. IAM doesn't control Postgres writes (and does nothing on local Docker), so it's no longer drawn as a layer.
    • Verifier no longer touches Postgres directly — it goes through MCP like every other agent.
    • Load semantics pinned. Files are deltas; live keeps the contract column cust_status; the fix is mapping v2 (customer_status → cust_status), published with the swap so tomorrow's load passes. Check 1 = live-before + file rows; check 4 = a sample of the file matches what landed.
    • Dashboard publisher. A static S3 site can't query Postgres, so a publisher Lambda writes it after sign-off.
    • Bedrock. Model access is automatic now; Phase 0 should confirm which Nova Micro ID works in Sydney (it may need the apac. inference profile).
    • Phase 8. Delete the RDS instance rather than stop it (a stopped instance restarts itself after 7 days), and price NAT or VPC endpoints for the demo day.

    Decision needed

    Where do Phases 1–7 run?

    Plan v1.0 keeps Postgres in Docker on your Mac but deploys Lambdas only through GitHub. A cloud Lambda can't reach your Mac, so the deployed topology drawn above only works from Phase 8.

    Recommended: run the pipeline job, agent runtime and MCP tool servers on your Mac with uv against Docker Postgres. Bedrock, S3, DynamoDB, SNS and X-Ray are the real AWS services via the apa profile. Phase 8 deploys the same code to Lambda and RDS.

    Alternative: a database Lambda can reach from day one. It costs NAT or VPC endpoints, which the plan's budget doesn't include.
