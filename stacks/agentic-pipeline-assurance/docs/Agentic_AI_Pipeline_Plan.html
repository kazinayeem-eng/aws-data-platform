Agentic Pipeline Assurance: build the 20-term agentic system

A working multi-agent incident-response system, built phase by phase from the Agentic AI Pipeline Walkthrough. One failed overnight load, an Orchestrator coordinating four specialist agents, a human approval, and a verified fix — built on the Mac against real AWS services, for a portfolio, at 2–3 hours a week.

Version v2.0 — draft Date 20 Nov 2026 Status DRAFT Owner Kazi Region ap-southeast-2 (Sydney) Budget ceiling US $10 / month

1 · Summary — read this first

What we are building, what it costs, what could go wrong

The problem. The walkthrough shows a complete agentic system on paper: an overnight data load fails at 02:14 from a renamed column, and four agents plus a human fix it safely before the 08:00 deadline. Kazi wants to learn agentic AI by building that system for real — and to end up with a portfolio piece that proves it, not a demo that only works on a laptop.

The recommendation. Build it in 9 phases over 20 weeks at 2–3 hours a week, following the v1.1 architecture. Python throughout. Strands Agents SDK for the agents, Amazon Bedrock (Nova Micro) for the model, S3 for raw files, PostgreSQL with pgvector for the analytics table and RAG, DynamoDB for memory (apa-memory) and approvals (apa-approvals), Step Functions plus SNS for the human approval. Phases 1–7 run on the Mac — the pipeline job, the agent runtime and the MCP tool servers run locally with uv against Docker Postgres, calling Bedrock, S3, DynamoDB, SNS and X-Ray as real AWS services via the apa profile. Phase 8 deploys the same code to Lambda and RDS. Every one of the 20 terms from the walkthrough is built, in a named phase, with a test that proves it works.

The cost. About US $1–3 a month while building (Bedrock tokens and S3, essentially), provided the database lives on the Mac during development and RDS is only switched on for the final demo, then deleted (with a snapshot). If RDS is left running 24/7 it adds about $13–15 a month on its own — see §10 and ADR-004.

The top three risks. (1) Time: 2–3 hours a week is thin, so phases are sized to one sitting each and every phase ends in something working. (2) Bedrock model access in Sydney: Nova Micro may need an apac. cross-region inference profile ID rather than the plain model ID — Phase 0 Spike B tests which ID works before any agent runs. (3) Scope creep: all 20 terms is a lot, so the plan is phased with gates — a phase does not start until the previous one passes its checks.

What I am asking you to approve. This plan as written — stack, phases, budget rule, and the definition of done for each phase. No code is written until you say yes. If you disagree with any ADR in §8, that is the place to argue: each one names the alternative it rejected.

2 · Goals, non-goals, constraints

What “done” means — and what it does not

Goals

  • Learn by building, not by reading. Every term in the walkthrough is implemented, not just described. If a term has no code and no test, it is not done.
  • End with a portfolio piece. A public-ready repo with a README a stranger can follow, architecture docs, tests, a recorded demo of the 02:14 incident fixing itself, and a cost screenshot proving the $10 ceiling.
  • Stay inside US $10/month, every month. The budget is a design constraint, not a hope. §10 prices every service; §11 names the traps.
  • Fit a real calendar. 2–3 hours a week, on a Mac, in Python at “can write scripts, not apps” level. Phases are sized to that.

Non-goals (explicitly out of scope)

  • Production readiness for real customer data. This uses synthetic customer data only. No real PII, ever.
  • High availability, multi-region, or scale beyond one nightly run. One run a night, on demand, is the load.
  • A managed-agent service (Bedrock Agents, AgentCore Runtime) as the primary runtime. We build on the SDK so the learning is in the code, not the console.
  • Fine-tuning a model. Prompting, tools, retrieval and guardrails are the levers here.

5 · C4 level 3 — Components

Inside the agent runtime

Only one container is complex enough to need a level-3 diagram: the agent runtime. Everything in it is a Python module with one job. If a module's job cannot be stated in one sentence, it is two modules.

Figure 3 — Agent runtime components. The Orchestrator is the hub: it briefs each specialist and validates every handoff before the next agent acts — no agent hands work directly to another. The four specialist agents are Strands Agent objects with different system prompts and different tool allow-lists — not four codebases. The interesting engineering lives in the supporting modules: the context builder (what the agent is allowed to see), the guardrail hooks (what it is never allowed to do), and the handoff package (how agents pass work without losing information). When approval is needed the runtime returns control to Step Functions, which sends the SNS email and waits — the wait does not live in the agent runtime. The Verifier checks through MCP tools like every other agent; it has no direct Postgres access. Diagrams scroll sideways on narrow screens.

6 · Dynamic view — one incident, end to end

02:14 to 08:00, step by step

The sequence is the acceptance test for the whole system. If the built system cannot replay these steps against the seeded incident, it is not done — whichever phase it is in.

Figure 4 — Sequence (22 steps). Every handoff passes through the Orchestrator, which validates it before briefing the next agent — no agent hands work directly to another. Steps 9, 13, 14 and 15 are the steps most tutorials skip and this plan does not: the blocked overwrite (guardrails), the pause (Step Functions holds the wait with waitForTaskToken while the SNS email is out), the approval through a confirm page, and the approval record written to apa-approvals — the swap tool checks that record itself, so the swap cannot run without a matching, unexpired, single-use approval. Step 7 is the RAG retrieval: the Diagnoser calls search_runbook and pulls runbook 4.2 + contract v3 from pgvector, rather than the model guessing from memory. The Verifier checks twice: the test copy in step 12, before any approval is requested, and live in step 20, after the swap — a failed post-swap check rolls back to customers_prev. A build that skips from step 8 to step 18 has built a demo, not the system. Diagrams scroll sideways on narrow screens.

Synthetic data only. The seeder generates 1.2M plausible customer rows locally; no real names, emails, or customer data are ever loaded. Load semantics, pinned: files are nightly deltas. Live keeps the contract column cust_status; the rename (cust_status → customer_status) happens in the file, not in live — nothing in live drifted. The fix is mapping v2 (customer_status → cust_status), published with the swap so tomorrow's load passes. customers_test is cloned from live first, so a swap is safe, and the old live table is kept as customers_prev for rollback. The rename is applied by the seeder on demand, so the incident is reproducible on any night.

Interfaces — the contracts agents must honour

MCP tools (each a FastMCP tool, each with a typed schema). read_job_logs(job, since) → log lines; get_table_schema(table) → columns; search_runbook(query) → ranked chunks with sources; write_test_copy(mapping) → row count + errors; run_checks(table) → the 4 checks with pass/fail; swap_tables(test, live) → only callable after approval, enforced by the tool server checking the apa-approvals record (matching incident AND test-copy hash, unexpired, unused), not by the agent promising; publish_mapping(version) → records mapping v2 so tomorrow's load uses it. The Verifier calls run_checks through MCP like every other agent — it has no direct Postgres access. Tools return data, never prose. An agent that wants a fact calls a tool; an agent that guesses is a bug.

A2A messages. Task request / task accepted / task result, using the A2A protocol over HTTP between the Orchestrator and specialists when they run as separate services in Phase 6. In earlier phases the same message shapes travel in-process — same schema, different transport, so Phase 6 changes deployment, not logic.

Handoff package (validated, typed).

{
  "done": "cause confirmed: column rename",
  "next": "update mapping, reload tonight's data",
  "owner": "fixer-01",
  "evidence": ["log 02:14 'Column not found'",
               "schema diff source vs mapping",
               "change note 17:40 yesterday"],
  "do_not_touch": ["analytics.customers (live)"]
}

Human approval payload (SNS email). What broke, what was tested (test-copy row count, errors, and the Verifier's 4-check result), exactly what will change (swap customers_test → customers, publish mapping v2), and what happens if it is not approved. The email links to a confirmation page on the approve endpoint (Lambda Function URL) — a scanner prefetching the link cannot approve; approving needs a deliberate click, which sends a signed single-use token. The endpoint checks the token and writes the approval to apa-approvals. No approval, no swap — the swap tool refuses without a matching approval record.

Matching approval, defined. A record in apa-approvals matches only if it names this incident ID, the hash of this test copy, has not expired, and has not been used before. The swap tool checks all four; a record that fails any of them is refused. The Step Functions wait (waitForTaskToken) times out after 30 minutes — if the human has not approved by then, the incident stays open and the live table is untouched.

8 · Architecture decisions

ADRs — each decision, and what it beat

Status: ACCEPTED — ADR-001…010 were all decided by Kazi on 18 Nov 2026. ADR-011 is new in v2.0 (20 Nov 2026) and is DRAFT until this plan is approved. These live in the repo at docs/adr/ from Phase 0.

ADR-001 — Strands Agents SDK as the agent framework

Context. The system needs a model-driven agent loop, MCP tool consumption, multi-agent patterns, human-approval interrupts, and tracing — and the builder is learning, so the framework must not demand framework expertise first.

Decision. Use Strands Agents SDK (Python), with Amazon Bedrock as the model provider.

Alternatives considered. LangGraph — explicit graph control and the best debugging story, but every step is hand-wired, which is more framework to learn before the first agent runs. Bedrock Agents (managed) — no code, but the learning goal is the code, and console configuration cannot be reviewed in a repo. Raw boto3 + hand-rolled loop — maximum learning about the loop, but re-implements retries, tool parsing and interrupts badly.

Consequences. Fastest path to a working agent; MCP and A2A are native, not adapters. Cost: the agent loop's behaviour is partly the framework's, so the plan includes reading the loop code in Phase 2 rather than treating it as magic. Revisit if: Strands cannot express the approval handoff cleanly in Phase 4 — LangGraph is the named fallback.

ADR-002 — Amazon Bedrock, Nova Micro as the default model

Context. Agents need a model that is cheap enough to run hundreds of learning iterations, available in ap-southeast-2, and capable enough to follow tool schemas.

Decision. Bedrock with Nova Micro by default; Claude Haiku used for one comparison run in Phase 7 so the evals can show the cost/quality trade-off with numbers.

Model access. Bedrock now grants access to serverless foundation models by default — no per-model access request. Anthropic models still need a one-time usage form. Nova Micro in Sydney may need an apac. cross-region inference profile ID rather than the plain model ID amazon.nova-micro-v1:0; Phase 0 Spike B tests which ID works and records the working ID here.

Alternatives considered. Claude Sonnet as default — better reasoning, but roughly 10–20× the token price; unjustifiable while the loop itself is what is being learned. Local models via Ollama — free, but tool-calling reliability on small local models is poor and would teach the wrong lessons about agent behaviour. OpenAI API — fine model, wrong cloud: it adds a second bill and a second credential for no benefit.

Consequences. Model spend stays in cents. The evals in Phase 5 are model-specific and must be re-run if the model changes — that is documented, not hidden. Revisit if: Nova Micro fails the tool-calling evals in Phase 5 (pass mark: 20-case set ≥ 17/20, §11); Haiku becomes the default and the cost model is re-priced.

ADR-003 — PostgreSQL + pgvector for the table, the sandbox, and RAG

Context. The system needs a relational analytics table, a scratch copy for safe testing, and vector search over runbooks. The budget forbids a dedicated vector database.

Decision. One PostgreSQL database (pgvector extension) holds customers, customers_test, and the documents embedding table.

Alternatives considered. Bedrock Knowledge Bases + OpenSearch Serverless — the AWS-native RAG path, but OpenSearch Serverless has a ~$70/month minimum: seven times the entire budget, before a single query. DynamoDB + a separate vector store — two stores, two bills, and DynamoDB is a poor fit for the analytics table. SQLite + local vectors — free, but SQLite cannot be the deployed analytics table, so the deployment would diverge from development.

Consequences. One database to learn, one to pay for, and retrieval quality is measurable with a 10-question test. Cost: pgvector at 1.2M-row scale is not a production vector store; nobody should claim it is. Revisit if: retrieval precision falls below the Phase 3 pass mark after chunking and prompt fixes.

ADR-004 — Mac-local for Phases 1–7; RDS only for the Phase 8 demo, then deleted

Context. The account is paid, so the 12-month RDS free tier is assumed expired. An RDS db.t3.micro left running costs ~$13–15/month — over budget alone. And a cloud Lambda cannot reach a database on the Mac, so the topology must be decided before any phase is written: either the database moves to the cloud (and the plan must price the VPC), or the code runs on the Mac (and Phase 8 is the deployment).

Decision. Phases 1–7 run on the Mac: the pipeline job, the agent runtime and the MCP tool servers run locally with uv against PostgreSQL in Docker, calling Bedrock, S3, DynamoDB, SNS and X-Ray as real AWS services via the apa profile. The deployed Lambda path (ADR-005/ADR-010) is the Phase 8 target, not how Phases 1–7 execute — no phase's definition of done requires a cloud Lambda to reach the Mac. RDS is deployed once, in Phase 8, for the recorded demo, and deleted the same day (with a snapshot) — not stopped, because a stopped RDS instance auto-restarts after 7 days. This keeps Phases 1–7 free of VPC costs: no NAT gateway, no VPC endpoints.

Alternatives considered. RDS from Phase 1, left running — simplest, but breaches the budget every month. RDS from Phase 1 in a VPC — Lambdas in a VPC need NAT or VPC endpoints to reach Bedrock and SNS; NAT alone adds ~$30/month and breaks the budget. RDS started/stopped per session — saves money but adds a start/stop ritual to every 2-hour session and teaches nothing. Neon/Supabase free tier — genuinely free Postgres with pgvector, but it moves the database off AWS and weakens the “built on AWS” portfolio story.

Consequences. Build cost stays at $1–3/month and no VPC is needed until Phase 8. The deployment step is practised exactly once, deliberately, in Phase 8 — and the demo recording is the evidence it worked. The Mac-local code and the deployed Lambda code are the same Python (uv packaging, ADR-009), so Phase 8 is a deployment change, not a rewrite. Revisit if: the account is found to still hold RDS free-tier hours in the Phase 0 spike (Spike A), in which case RDS can be used from Phase 1 at no cost — but only if the VPC cost is also covered.

ADR-005 — Lambda for every job and tool; no EC2, no AgentCore Runtime as primary

Context. Jobs and tools need somewhere to run. The always-free Lambda allowance (1M requests + 400,000 GB-seconds/month) covers this workload many times over.

Decision. Ingest, transform, MCP tool servers and the agent runtime all run as Lambda functions in the deployed (Phase 8) topology, and locally on the Mac during Phases 1–7 (ADR-004). No EC2.

Alternatives considered. Bedrock AgentCore Runtime — the managed agent host, but it is pay-per-use with no free tier and hides the runtime the portfolio is meant to demonstrate. EC2 t3.micro — a familiar server, but it must be patched, kept running, and paid for when idle. ECS/Fargate — the right answer at real scale, and the wrong answer for one nightly run.

Consequences. Zero idle cost; cold starts are irrelevant at one run a night. Cost: Lambda's 15-minute limit constrains the transform job — the seeded load is sized to finish in under 5 minutes, and the plan says so explicitly. The human approval wait never sits inside a Lambda — Step Functions holds it with waitForTaskToken (§7), so the 15-minute cap cannot be hit by an 18-minute human. Revisit if: a phase needs a long-running process (it should not — see §11).

ADR-006 — Step Functions orchestrates the pipeline; Strands orchestrates the agents

Context. Two different orchestration problems exist: the nightly pipeline (a fixed sequence with a failure branch) and the incident response (a goal split into tasks, with a human decision in the middle). One tool for both would be a compromise.

Decision. Step Functions owns the pipeline: schedule → load → on failure, invoke agents → on approval-needed, send the SNS email and hold the wait with waitForTaskToken (30-minute timeout) → on approval, resume → on success, finish. Strands owns the agent teamwork: the Orchestrator agent splits the goal and delegates. The boundary is the failure event, and the return is the approval decision.

Alternatives considered. Everything in Step Functions — visible and robust, but agent reasoning does not belong in a state machine; every prompt change becomes a deployment. Everything in Strands — the pipeline schedule and retries would be re-implemented in Python for no benefit. Cron + Lambda chaining — works, but failures are invisible compared with a state-machine execution view.

Consequences. Each orchestrator does what it is good at, and the portfolio shows both. Cost: two things to learn instead of one — Phase 1 teaches Step Functions before any agent exists, so the learning is sequenced.

ADR-007 — DynamoDB for memory; no separate memory service

Context. Agents need short-term memory (this run) and long-term memory (past incidents). Managed memory services exist, but they are another bill and another API.

Decision. DynamoDB table apa-memory, on-demand, inside the always-free allowance. Short-term notes are written per run; long-term lessons are explicit records, not embeddings. Approvals are NOT stored here — they live in apa-approvals (ADR-011), in a separate trust boundary.

Alternatives considered. Bedrock AgentCore Memory — managed and good, but pay-per-use and it would hide the memory design the portfolio is meant to show. Postgres for memory too — possible, but mixing run memory into the analytics database blurs the boundary the architecture is trying to teach. Files on disk / in S3 — free, but no querying and no story about memory as a system component.

Consequences. Memory is a visible, testable design: the Phase 3 test proves a lesson changes the diagnosis. Cost: DynamoDB's data model (partition/sort keys) must be learned in Phase 3 — it is scoped to one table and one access pattern, deliberately.

ADR-008 — Evals are a fixed 20-case set, run on every change; no eval platform

Context. “It worked once” is not evidence. The portfolio needs repeatable proof that the agents behave — and that a change did not break them.

Decision. A versioned set of 20 eval cases (10 retrieval, 5 diagnosis, 5 end-to-end incident replays) run by a plain pytest script, scored automatically, with results committed to the repo. No third-party eval platform.

Alternatives considered. LangSmith / Langfuse hosted — better tooling, but another account, another bill, and hosted traces of a learning project. Manual “try it and see” — the default for tutorials and the reason most agent demos cannot be trusted. Bedrock model evaluation jobs — useful for the Phase 7 model comparison only, not for the daily loop.

Consequences. Every phase gate includes “evals still pass”. The eval set itself is a portfolio artefact a reviewer can run. Cost: writing good eval cases is real work — it is budgeted as its own phase (Phase 5), not squeezed into a Friday night.

ADR-009 — uv as the Python package and environment manager

Context. The project needs reproducible Python environments on the Mac and in CI, with pinned dependencies a reviewer can reproduce exactly. Phase 0 needs to name one tool for this, not leave it to chance.

Decision. Use uv (Astral) for everything Python: uv python install 3.12 for the interpreter, uv init / uv add for dependencies, uv sync to build the environment, uv run to execute. Dependencies are declared in pyproject.toml and pinned in the committed uv.lock lockfile.

The one wrinkle, and how it is handled. Lambda deployment packages are built from the lockfile, not by hand: CI runs uv export --format requirements-txt, installs into a target directory, zips it, uploads the zip to S3, and passes the S3 location to CloudFormation as a parameter (see ADR-010). Local development and tests run under uv run; the packaged zip is what gets deployed. No other ADR changes.

Alternatives considered. pip + venv (original plan) — works, but no lockfile, so “works on my machine” is a real risk for a portfolio repo. Poetry — lockfile and good UX, but slower, heavier, and its Lambda story is worse than uv's export path. pip-tools — lockfile via pip-compile, but it is two tools doing what uv does in one.

Consequences. Reproducible environments from one lockfile; faster installs; one tool instead of three. Cost: uv is a new tool to learn in Phase 0 — budgeted there, about 30 minutes, and it replaces the venv lesson rather than adding to it. Revisit if: uv export output ever fails a CloudFormation deploy, in which case the fallback is a hand-maintained requirements.txt checked by CI against the lockfile.

ADR-010 — CloudFormation templates, deployed by GitHub Actions

Context. Kazi prefers native CloudFormation templates deployed through a GitHub pipeline. The deployment story must still be reviewable in the repo, repeatable, and fully deletable — and for a portfolio, a CI/CD pipeline is itself evidence.

Decision. Infrastructure is plain CloudFormation YAML in infra/ (one root template, infra/main.yaml, with the Step Functions definition written as JSON/YAML by hand). Deployment runs in GitHub Actions: on push to main (and on manual dispatch), the workflow builds the Lambda zips from the uv lockfile, uploads them to a deployment S3 bucket, then runs aws cloudformation deploy. GitHub authenticates to AWS with OIDC — no long-lived AWS access keys stored in GitHub. The OIDC trust policy allows only this repo's own branches and the named workflows — fork pull requests cannot assume the role, so a fork cannot spend the Bedrock budget. The deploy workflow runs only on push to main (and manual dispatch), never on fork PRs. A second workflow runs the evals and unit tests on every pull request. Nothing is deployed from the Mac; the console is for reading (logs, traces, executions), not for creating resources.

Alternatives considered. CDK (Python) — more expressive, but a second framework to learn in Phase 0 and its generated templates are harder to read in a portfolio review. Terraform — excellent, but another tool and a state file, with no advantage at this scale. Manual aws cloudformation deploy from the Mac — works, but unreviewable as a process and it teaches nothing about CI/CD.

Consequences. The Lambda packaging step must be scripted explicitly (scripts/build.sh: uv export → install to target dir → zip → upload to S3). The project reuses the existing repo pipeline — OIDC role, deploy.yml (dev → prod) and pr-validate.yml (cfn-lint) in kazinayeem-eng/aws-data-platform — so Phase 0 adds a stack to a working pipeline instead of building one. In exchange: every deployment is a reviewed, repeatable pipeline run; the portfolio shows CI/CD, not just code; and there is no layer between the repo and AWS. Cost: GitHub Actions is free for public repos; OIDC costs nothing. Revisit if: the CloudFormation template grows past ~500 lines, at which point splitting it into nested stacks is the fix — not a move to CDK.

Status. ACCEPTED 18 Nov 2026 — decided by Kazi.

ADR-011 — Approvals in their own DynamoDB table; only the approve endpoint writes

Context. The swap must not run without a human approval, and the approval must be checkable by the tool that performs the swap. If the approval record lives in the same table the agents write memory to, any agent that can write memory can approve its own work — the Fixer could approve itself.

Decision. A separate DynamoDB table apa-approvals, on-demand, inside the always-free allowance. Only the approve endpoint (Lambda Function URL) can write to it. The approval record is bound to the incident ID, the hash of the test copy, an expiry, and a single-use flag. swap_tables reads the record and refuses unless all four match. The email link opens a confirmation page (so a scanner prefetching the link cannot approve); approving needs a deliberate click that sends a signed single-use token.

Alternatives considered. Approval record in apa-memory — one fewer table, but the Fixer writes memory, so it could write its own approval; rejected on the trust boundary. Key-scoped IAM on one table — DynamoDB item-level IAM is coarse and hard to audit; a separate table is a clearer boundary. Approval as a Step Functions token only, no table — the token proves the human clicked, but the swap tool needs a durable, checkable record tied to the test copy's hash; the token alone does not carry it.

Consequences. The approval is a durable, auditable record a reviewer can read. Cost: one more on-demand table inside the always-free allowance — $0. The approve endpoint is a second Lambda to deploy (Phase 4), and the confirm page is a small static page. Revisit if: the approval flow needs more than one approver, in which case the record gains an approver field — the table shape, not the boundary, changes.

Status. DRAFT 20 Nov 2026 — new in v2.0, for approval with this plan.

Phase 1 — The pipeline, no agents (2 weeks) · Term 1 (Agentic Pipeline, pipeline half)

Entry: Phase 0 gate passedTime: 2 weeksCost: < $1

Goal. The nightly load exists, works, and fails in exactly the way the walkthrough describes — before any agent is allowed near it.

  • Seeder generates 1.2M synthetic customer rows into the local Postgres customers table (3 years of history).
  • S3 bucket with 7-day lifecycle expiry; simulated source writes the nightly CSV.
  • Lambda ingest + transform, driven by a Step Functions state machine on an EventBridge 02:00 schedule (plus a manual trigger for learning). The load is schedule-driven only — there is no S3 event trigger on ingest.
  • Failure injection: a seeder flag renames cust_status → customer_status; the transform fails with the exact error from the walkthrough.
  • Static dashboard (the walkthrough's result section, simplified) plus a publisher Lambda that writes the verified numbers to it — a static S3 site cannot query Postgres, so the publisher reads the table and writes the dashboard. Freshness is a load timestamp written by the transform on each run — not the newest signup_date.

Definition of done. A clean run loads and the publisher writes fresh numbers to the dashboard; a renamed-column run fails, the Step Functions execution shows the failure branch, and the dashboard shows stale numbers. Both are reproducible on demand.

Phase 2 — Detector, tools, and the agent loop (2 weeks) · Terms 3, 6, 7, 11

Entry: Phase 1 gate passedTime: 2 weeksCost: < $1

Goal. The first agent, and the discipline it runs under: tools, not guesses; a brief, not the whole log file.

  • FastMCP tool server with read_job_logs and get_table_schema; tools return typed data.
  • Detector agent (Strands) with a 2-tool allow-list; the agent loop (perceive → plan → act → observe) is visible in logs.
  • Context builder: the Detector's brief contains exactly 6 items — schema diff, runbook, owner, target, rules, deadline — and nothing else. A test asserts a known raw log line is absent from the brief.
  • Read the Strands loop code once, and write a one-paragraph note in the repo explaining what it does — no magic boxes.

Definition of done. Given a failed run, the Detector reports the missing column and cites the get_table_schema result. Adding a third tool requires no change to the Detector's code. The brief-size test passes.

Phase 3 — Diagnoser: RAG, memory, grounding (2 weeks) · Terms 8, 14, 15

Entry: Phase 2 gate passedTime: 2 weeksCost: < $1

Goal. The diagnosis is evidence-based and remembers the past — the two things that separate an agent from a chatbot with tools.

  • Runbook 4.2 (“Handling column renames”) and the customers data contract written as short Markdown, chunked, embedded with Bedrock Titan, stored in the pgvector documents table.
  • search_runbook tool; Diagnoser retrieves before it explains.
  • DynamoDB apa-memory: short-term notes for the run; one long-term lesson (the September orders-table rename, fix: update the mapping).
  • Grounding rule enforced in code: every claim in the diagnosis carries a source reference; anything without one is rendered “unknown”.

Definition of done. A 10-question retrieval test scores ≥ 8/10. The diagnosis for the seeded incident cites the log line, the schema diff, and the change note. Deleting the September lesson changes the Diagnoser's suggested fix — proving memory is load-bearing, not decorative.

Phase 4 — Fixer: sandbox, guardrails, policy, identity, human approval (4 weeks) · Terms 5, 9, 10, 16, 17

Entry: Phase 3 gate passedTime: 4 weeksCost: < $1

Goal. The most important phase. The Fixer can repair the table — and cannot destroy it. This is the phase the portfolio is really about.

  • write_test_copy: builds customers_test with the new mapping and loads tonight's files; reports rows and errors.
  • Guardrail hook + tool-server authorisation + Postgres role: any attempt to overwrite the live table in one step is blocked before the call lands, logged, and the agent must re-plan. All three layers refuse independently — test each one on its own (disable the hook and the tool server still refuses; call as the Fixer role and Postgres still refuses). The blocked attempt leaves the live table byte-identical (row count + hash).
  • Agent identity: separate Postgres roles per agent, and the tool server authenticates which agent is calling. The Fixer's Postgres role can read production and write staging, and cannot write production. Test tries, and fails. (IAM roles do not control Postgres writes.)
  • Policy: swap_tables refuses unless a matching approval record exists in apa-approvals (incident ID + test-copy hash + unexpired + unused). The check lives in the tool server, not in the prompt.
  • Approve endpoint (Lambda Function URL) + apa-approvals table: the endpoint serves the confirm page, checks the signed single-use token, and writes the approval record. Only the endpoint can write to apa-approvals.
  • Human-in-the-loop: SNS email with what broke, what was tested (test-copy row count and errors), and exactly what will change; the email links to the confirm page. Step Functions holds the wait with waitForTaskToken (30-minute timeout). A timeout or rejection leaves the live table alone and the incident open. (Phase 5 adds the Verifier's 4-check result to the email.)

Definition of done. The full Fixer path runs end to end: blocked overwrite → test copy loads with 0 errors → approval email → confirm page → approval → swap → dashboard fresh. And the negative paths all hold: no approval means no swap; a blocked overwrite changes nothing; a rejected approval leaves the live table alone.

Phase 5 — Verifier and the eval set (2 weeks) · Term 18

Entry: Phase 4 gate passedTime: 2 weeksCost: < $1

Goal. Proof replaces “it worked on my machine”. The system can now say, with numbers, whether a change helped or hurt.

  • run_checks: the 4 checks (row count = live-before + file rows; column names match the contract and no null keys; status values in the contract set; 100-row sample matches the source) with pass/fail each.
  • Verifier wired into the flow: the approval request now carries the pre-approval 4-check result (a failing check blocks the approval request); after the swap, the Verifier re-runs the 4 checks on live, and a failure rolls back to customers_prev.
  • 20-case eval set (10 retrieval, 5 diagnosis, 5 end-to-end replays) as a pytest suite; results written to a file committed with the change that produced them.
  • Deliberate-regression test: break the mapping on purpose and confirm the evals catch it.
  • GitHub Actions runs the evals on every push (free for public repos).

Definition of done. The 4 checks pass 4/4 on a fixed table (test copy and live). The eval suite runs in CI and scores ≥ 17/20 (85%) — the pass mark (§11). The deliberate regression turns it red. The eval set is documented well enough that a reviewer can run it.

Phase 6 — Orchestrator, multi-agent, A2A, handoffs (2 weeks) · Terms 2, 4, 12, 13

Entry: Phase 5 gate passedTime: 2 weeksCost: < $1

Goal. Four specialists become a team: one goal in, four tasks out, work passed without loss.

  • Orchestrator agent: reads the goal, splits it into the four tasks, assigns them, validates every handoff before the next agent acts, and decides when a human is needed.
  • Agents run as separate Strands agents; task requests travel over A2A (in-process in this phase, same message schema as HTTP).
  • Handoff package validated on receipt: a handoff missing evidence or do_not_touch is rejected and the run stops cleanly with an error, not a guess.
  • End-to-end run with no human involvement except the approval step.

Definition of done. The seeded incident runs from alert to verified fix with the Orchestrator delegating and the four agents handing off, and the full 22-step sequence (Figure 4) replays end to end. A malformed handoff is rejected by validation. Removing any one agent makes its phase's test fail — proving each agent is load-bearing.

Phase 7 — Observability, protocols, model comparison (3 weeks) · Terms 19, 20

Entry: Phase 6 gate passedTime: 3 weeksCost: $1–2

Goal. The system can explain itself after the fact, its parts are swappable, and the model choice is a measured decision instead of a preference.

  • OpenTelemetry traces from the runtime to X-Ray; one trace per incident, replayable: who acted, which tool, what came back.
  • CloudWatch dashboard: runs, failures, approvals, blocks, eval scores over time.
  • Protocol test: the Fixer is replaced with a differently-built agent behind the same MCP/A2A contracts; nothing else changes and the evals still pass.
  • Model comparison: the 20-case eval set run on Nova Micro and on Claude Haiku; cost per run and score published side by side in the README.

Definition of done. A reviewer can open one trace and reconstruct the whole incident. The swapped Fixer passes evals. The model comparison table exists with real numbers, and the default model (ADR-002) is either confirmed or changed by a new ADR.

Testing strategy (one paragraph, no hand-waving)

Three layers. Unit tests (pytest) for the context builder, the handoff validator, the guardrail hook, and the check functions — these run in milliseconds and in CI on every push. Integration tests run the tools against the local Docker Postgres and the seeded incident — these run before a phase is called done. Evals (ADR-008) are the 20-case set scored on every change; they are the only test that judges agent behaviour, and they are the gate between phases. No layer substitutes for another: a green unit suite with failing evals means the code is correct and the system is wrong.

Eval pass mark (§11). The 20-case eval set must score ≥ 17/20 (85%) on every run, and the 4 checks must pass 4/4 on a fixed table (test copy and live). A change that drops the eval score below 17/20, or breaks a check, does not merge — the evals are the gate between phases (ADR-008). If Nova Micro cannot reach the pass mark, ADR-002 is revisited (Haiku default) and the cost model is re-priced.
